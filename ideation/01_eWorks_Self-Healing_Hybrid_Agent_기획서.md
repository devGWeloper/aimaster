## 0. v0.1 대비 변경 요약

v0.1은 "요청 → 툴 선택 → 레거시에 JSON 요청 전송"으로 끝나는 구조라, 사람이 툴을 미리 하나하나 등록해야 했고 에이전트는 등록된 API를 고르기만 했다. v0.2에서는 에이전트가 레거시 모듈을 직접 찾아서 이해하고, 조합해서 실행한다.

| 구분 | v0.1 (기존) | v0.2 (변경) |
| --- | --- | --- |
| 레거시 연동 | 사람이 정의한 툴 API에 JSON 메시지 전송 | AI가 레거시 소스를 분석해 **모듈 카탈로그를 자동 생성**하고, 모듈 함수를 **직접 실행** |
| 처리 단위 | 단일 툴 호출 | 단일 모듈 호출 + **여러 모듈을 엮은 실행 계획(코드)** |
| 안전장치 | 없음(툴 단위 신뢰) | 부작용 등급(조회/변경/비가역), Dry-run, DB 스냅샷 롤백, 승인 게이트 |
| 자가 수정 대상 | 프롬프트·툴 코드 | 프롬프트 + **어댑터 코드 + 모듈 카드 + 라우팅 임계값** (레거시 원본은 수정 금지) |
| 학습 축적 | 없음 | 성공한 다단계 실행 계획을 **스킬**로 저장 → 다음부터 Jev 경로로 빠르게 처리 |
| 신규 기능 대응 | 사람이 툴 추가 | 레거시에 모듈이 추가되면 **자동 온보딩** |

## 1. 프로젝트 개요

### 프로젝트 명

eWorks Self-Healing Hybrid Agent: 레거시 모듈을 스스로 이해·실행·수리하는 Jev·LLM 하이브리드 업무 에이전트

### 한 줄 정의

사용자가 자연어로 업무를 요청하면, 에이전트가 레거시 eWorks의 어떤 모듈을 어떤 순서로 실행해야 하는지 스스로 판단해 안전하게 실행하고, 실패하면 원인을 찾아 자기 코드(어댑터·프롬프트·카탈로그)를 고친다.

---

## 2. 배경 및 문제 정의

* 현재 상황 (As-Is)
  * 사내 업무 시스템(eWorks)은 오래된 레거시 모듈(결재·경비·근태·구매·회의실·조직) 묶음이고, 문서화가 부족하며 코드값·날짜 형식·호출 순서 같은 암묵적 규칙이 많음
  * 업무 에이전트를 붙이려면 개발자가 모듈마다 툴 래퍼(API 스펙, JSON 스키마)를 수작업으로 만들어야 함
  * 모든 판단을 대형 LLM이 처리하고, 실패하면 개발자가 로그를 보고 프롬프트·툴 코드를 직접 고침

* Pain Point
  * 시간: 단순 조회도 LLM 생성 대기로 응답 지연. 새 레거시 기능 하나를 에이전트에 연결하는 데 수일 소요
  * 비용: 전체 요청 대부분을 차지하는 단순 판단에 고비용 LLM 호출 사용. 툴 래퍼 개발·유지보수 공수 발생
  * 품질: 레거시의 암묵적 규칙을 래퍼가 놓치면 같은 유형의 실패가 반복되고, 사람이 고칠 때까지 방치됨
  * 확장성: 여러 모듈을 엮어야 하는 요청(예: "반려된 경비 건 사유 고쳐서 재상신")은 툴 하나로 처리할 수 없음

* 기회 요인
  * 2026년 9월, 텍스트 대신 확률이 붙은 구조화 판단을 반환하는 System One 모델(Jev)이 등장해 단순 판단을 수십~수백 배 빠르고 저렴하게 처리할 수 있게 됨
  * 같은 달 Google RRSI 등 에이전트가 자기 하네스(프롬프트·툴·제어 코드)를 스스로 고치는 Recursive Self-Improvement 연구가 실용 단계에 진입
  * LLM의 코드 이해·생성 능력이 레거시 소스를 읽고 호출 방법을 추론하는 수준에 도달 (Code-as-Action 방식 확산)

## 4. 프로젝트 목표

### 정성적 목표

1. **레거시 자율 실행**: 사람이 툴을 등록하지 않아도 에이전트가 레거시 모듈을 탐색·이해·실행하는 구조 확립
2. **하이브리드 판단**: 판단 난이도에 따라 Jev(빠른 판단)와 LLM(계획·추론)을 자동 분배
3. **안전한 실행**: 변경·비가역 작업에 대한 부작용 등급 관리, Dry-run, 롤백, 승인 체계 구축
4. **자가 복구·진화**: 실패 원인을 스스로 분석해 하네스를 수정·검증하고, 성공 패턴은 스킬로 축적
5. **기술 내재화**: System One 모델, RRSI, Code-as-Action 기반 에이전트 기술 확보

### 정량적 목표 (KPI)

| 성과 지표 | 목표 수치 | 측정 방법 | 현재 수준 |
| --- | --- | --- | --- |
| 평균 응답 시간 | 50% 이상 단축 | 동일 테스트셋 기준 요청별 응답시간 | LLM 단독 베이스라인 측정 예정 |
| LLM 호출 비율 | 30% 이하 | 전체 요청 중 LLM 경로 처리 비율 | 100% |
| 단일 요청 성공률 | 95% 이상 | 단일 모듈 요청 테스트셋 정답률 | 측정 예정 |
| 다단계 요청 성공률 | 80% 이상 | 2개 이상 모듈 조합 요청 테스트셋 정답률(최종 DB 상태 비교) | 측정 예정 |
| 모듈 자동 온보딩율 | 80% 이상 | 신규 모듈 중 사람 개입 없이 카탈로그 등록 + 실행 성공한 비율 | 0% (전량 수작업) |
| 실패 자가 복구율 | 60% 이상 | 실패 유형 중 사람 개입 없이 수정·검증 통과한 비율 | 0% |
| Held-out 성능 향상 | 진화 전 대비 +10%p | 진화에 쓰지 않은 테스트셋 성공률 비교 | 베이스라인 측정 예정 |
| 무승인 변경 작업 실행 | **0건** | 변경·비가역 등급 모듈이 승인 없이 실제 반영된 건수 | - |

## 5. 시스템 구성

### 5.1 전체 아키텍처

```
┌──────────────────────────────────────────────────────────────────────────┐
│  사용자 UI (채팅 + 실행 트레이스 + 승인 패널 + 자가 수정 리포트)              │
└───────────────┬──────────────────────────────────────────────────────────┘
                │ 자연어 요청
┌───────────────▼──────────────────────────────────────────────────────────┐
│  ① 하이브리드 라우터                                                       │
│     Jev: 의도 / 대상 모듈(또는 스킬) / 파라미터 / 확신도 판단                  │
│     확신도 ≥ 임계값 & 단일 모듈·스킬 → Fast Path                             │
│     그 외 → LLM Planner (다단계 실행 계획 = 실행 코드 생성)                   │
└───────┬───────────────────────────────┬──────────────────────────────────┘
        │ 모듈 카드 / 스킬 조회             │
┌───────▼─────────────┐   ┌─────────────▼──────────────────────────────────┐
│ ② 모듈 카탈로그        │   │ ③ 실행 런타임 (샌드박스)                          │
│  - 모듈 카드(자동생성) │   │  - 실행 계획 정적 검사(허용 모듈·부작용 등급)         │
│  - 어댑터 코드         │   │  - Dry-run → 변경 예정 내역 산출                   │
│  - 스킬 라이브러리     │   │  - 승인 게이트(변경/비가역)                         │
└───────▲─────────────┘   │  - DB 스냅샷 → 실행 → 결과 검증 → 실패 시 롤백       │
        │ 소스 분석         │  - 실행 트레이스·감사 로그 기록                      │
┌───────┴─────────────┐   └─────────────┬──────────────────────────────────┘
│ ④ 모듈 탐색기          │                 │ Guard Proxy를 통해서만 호출
│  소스·시그니처·주석    │   ┌─────────────▼──────────────────────────────────┐
│  호출관계 분석 → 카드  │◄──│ ⑥ Mock Legacy eWorks                             │
│  생성 + 프로브 실행    │   │  approval / expense / attendance / purchase /    │
└─────────────────────┘   │  room / org  +  Mock DB(SQLite) + 장애 주입기       │
                          └────────────────────────────────────────────────┘
        ▲ 수정안 반영(승인 후)                │ 실패 트레이스
┌───────┴──────────────────────────────────────▼───────────────────────────┐
│  ⑤ 자가 수정 엔진 (RRSI)                                                   │
│   실패 수집·분류 → 수정안 생성(어댑터/카드/프롬프트/임계값) →                   │
│   evolve셋 검증 → leakage critic → held-out셋 검증 → 승인 → 반영/롤백         │
└──────────────────────────────────────────────────────────────────────────┘
```

### 5.2 요청 처리 흐름 (요약)

1. 사용자 요청 → Jev가 `{intent, target(module|skill), params, confidence}` 반환
2. **Fast Path**: 확신도 ≥ 임계값이고 대상이 단일 모듈 또는 등록된 스킬이면, 어댑터를 거쳐 모듈을 바로 실행
3. **Plan Path**: 그 외에는 LLM이 모듈 카드를 참고해 실행 계획(Python 코드)을 생성
4. 런타임이 계획을 정적 검사 → Dry-run → (변경 작업이면) 사용자 승인 → 실제 실행
5. 실행 결과를 사후 조건으로 검증하고, 실패하면 롤백한 뒤 실패 트레이스를 자가 수정 엔진에 전달
6. 성공한 Plan Path 실행은 스킬 후보로 등록

## 6. 핵심 기능 상세

### F1. Mock Legacy eWorks (목업 레거시 시스템)

실제 레거시 대신, **레거시의 불편한 특성을 의도적으로 재현한** 목업 시스템을 만든다. 에이전트가 풀어야 할 문제가 실제와 비슷해야 PoC 결과에 의미가 있기 때문이다.

**구성**
* Python 패키지 `legacy_eworks/` + SQLite Mock DB + 시드 데이터 생성기
* 레이어 구조는 실제 레거시처럼 `*Service` / `*Dao` / `common` 으로 구성
* 시드 데이터: 임직원 300명, 조직 25개, 결재 문서 2,000건, 경비 1,500건, 근태 6개월치, 구매요청 500건, 회의실 20개 (Faker 기반, 재현 가능하도록 seed 고정)

**모듈 목록 (초기 6개 도메인, 약 40개 함수)**

| 도메인 | 모듈 | 주요 함수 (예시) | 부작용 등급 |
| --- | --- | --- | --- |
| 공통 | `common.session` | `openSession(empNo)`, `closeSession()` | 조회 |
| 결재 | `approval.AprvService` | `getAprvLst`, `getAprvDtl`, `doAprv`, `doRjct`, `reqAprv` | 조회 / 변경 / 비가역 |
| 경비 | `expense.ExpnsService` | `selExpnsMst`, `selExpnsDtl`, `updExpnsRsn`, `submitExpns` | 조회 / 변경 / 비가역 |
| 근태 | `attendance.AttdService` | `getWorkHist`, `getRemainLeave`, `reqLeave`, `cnclLeave` | 조회 / 변경 |
| 구매 | `purchase.PrchService` | `getPrchReqLst`, `getBudgetRemain`, `crtPrchReq` | 조회 / 변경 |
| 회의실 | `room.RoomService` | `getRoomSchd`, `findEmptyRoom`, `rsvRoom`, `cnclRsv` | 조회 / 변경 |
| 조직 | `org.OrgService` | `getEmpInfo`, `getDeptMbr`, `getApprLine` | 조회 |
| 알림 | `notify.MailSender` | `sendMail` | 비가역 |

**의도적으로 넣는 레거시 특성 (= 에이전트가 극복해야 할 함정)**

| # | 특성 | 예시 | 에이전트가 해야 할 일 |
| --- | --- | --- | --- |
| L1 | 불친절한 이름 | `selExpnsMst`, `getAprvLst` | 소스·주석 분석으로 의미 추론 |
| L2 | 날짜 형식 혼재 | 결재는 `YYYYMMDD`, 경비는 `YYYY-MM`, 근태는 `datetime` | 어댑터에서 정규화 |
| L3 | 문서화 안 된 코드값 | 상태 `'A'`=승인, `'R'`=반려, `'P'`=대기, `'T'`=임시저장 | DAO/SQL에서 코드값 의미 추출 |
| L4 | 호출 순서 의존 | `openSession()` 없이 호출하면 `None` 반환 | 사전 조건으로 카드에 기록 |
| L5 | 조용한 실패 | 예외 대신 `-1` 또는 빈 리스트 반환 | 사후 조건 검증으로 실패 감지 |
| L6 | 페이지 제한 | 목록 조회 최대 50건, `pageNo` 필요 | 반복 호출 패턴을 어댑터화 |
| L7 | 폐기 예정 함수 | `getAprvLst_old` 가 아직 남아 있고 잘못된 결과 반환 | 호출 관계·주석으로 배제 |
| L8 | 숨은 부작용 | `submitExpns` 내부에서 `sendMail` 호출 | 호출 그래프로 부작용 등급 전파 |
| L9 | 권한 체크 누락 | 일부 조회 함수가 타인 데이터도 반환 | 가드 프록시에서 사용자 범위 강제 |

**장애 주입기 (Fault Injector)**
* 설정으로 특정 모듈에 지연·예외·스키마 변경(파라미터명 변경, 반환 필드 추가/삭제)을 주입
* 자가 수정 시나리오와 회귀 테스트용 실패 데이터를 의도적으로 만들어 내는 데 사용
* "레거시 버전 업" 시뮬레이션: 새 모듈 추가, 함수 시그니처 변경 → 자동 온보딩·자가 수정 검증

### F2. 모듈 탐색기 & 모듈 카탈로그

툴을 사람이 등록하는 대신, **레거시 소스를 읽어 모듈 카드를 자동으로 만든다.**

**탐색 단계**
1. 정적 분석: AST로 함수 시그니처, docstring/주석, 호출 그래프, SQL 문, 코드값 상수 추출
2. LLM 해석: 함수 목적, 파라미터 의미·형식, 반환 구조, 사전·사후 조건, 부작용 등급 추론
3. 프로브 실행: 샌드박스 + 스냅샷 DB에서 조회 함수를 샘플 파라미터로 실제 호출해 추론이 맞는지 확인 (변경 함수는 스냅샷 위에서만 실행 후 폐기)
4. 카드 등록: 검증된 카드를 카탈로그에 저장하고 Jev 판단 스키마(후보 모듈 enum)를 갱신

**모듈 카드 예시**

```yaml
id: expense.ExpnsService.selExpnsMst
summary: 사용자의 경비 정산 마스터 목록 조회
side_effect: read            # read | write | irreversible
preconditions:
  - common.session.openSession 호출 필요
params:
  empNo:   { type: str, desc: 사번, source: session }
  yyyymm:  { type: str, format: "YYYY-MM", desc: 정산월 }
  stsCd:   { type: str, enum: {P: 대기, A: 승인, R: 반려}, optional: true }
  pageNo:  { type: int, default: 1, note: "최대 50건/페이지" }

  - "빈 리스트: 조건 불일치 또는 세션 없음 (구분 불가 → 세션 사전 확인)"

```

**어댑터 레이어**
* 모듈 카드마다 얇은 어댑터 함수를 자동 생성: 날짜·코드값 정규화, 세션 처리, 페이지 반복, 조용한 실패 → 예외 변환
* 에이전트는 레거시를 어댑터를 통해서만 호출하고, **자가 수정의 주 대상도 어댑터**이다 (레거시 원본은 건드리지 않음)

### F3. 하이브리드 라우터 (Jev + LLM)

| 경로 | 조건 | 처리 | 목표 응답 |
| --- | --- | --- | --- |
| Fast Path (Jev) | 확신도 ≥ 임계값, 대상이 단일 모듈 또는 스킬 | Jev가 고른 모듈/스킬을 파라미터와 함께 바로 실행 | 1초 이내 |
| Plan Path (LLM) | 확신도 < 임계값, 다단계 필요, 모호한 요청 | LLM이 카드·스킬을 참고해 실행 계획 코드 생성 | 5~15초 |
| Clarify | 필수 파라미터를 추론할 수 없음 | 사용자에게 되묻기 (선택지 제시) | - |

* Jev 출력 스키마: `{intent, target_type: module|skill|plan, target_id, params, confidence, missing_params}`
* 임계값은 도메인·부작용 등급별로 따로 둔다 (조회 0.85 / 변경 0.95 / 비가역은 항상 승인)
* 라우팅 결정·확신도·실제 성공 여부를 모두 기록해 임계값 자동 튜닝에 사용

### F4. 모듈 실행 런타임 (Code-as-Action)

LLM이 만든 실행 계획은 JSON 툴 호출 나열이 아니라, **어댑터를 import해서 실제로 실행하는 Python 코드**다. 그래서 조건 분기, 반복, 중간 결과 가공을 계획 하나로 표현할 수 있다.

**실행 계획 예시** (요청: "지난달 반려된 경비 중에 증빙 누락으로 반려된 거 사유 보완해서 다시 올려줘")

```python
from adapters import expense, approval

rejected = expense.list_expenses(month="2026-09", status="REJECTED")
targets = [e for e in rejected if "증빙" in (e.reject_reason or "")]

for e in targets:
    expense.update_reason(e.id, reason=e.reason + " (영수증 첨부 완료)")   # write
    expense.submit(e.id)                                                  # irreversible (메일 발송 포함)

result({"resubmitted": [e.id for e in targets]})
```

**안전장치 단계**

| 단계 | 내용 |
| --- | --- |
| 1. 정적 검사 | 허용된 어댑터만 import 가능, 파일·네트워크·`os`/`subprocess` 차단, 호출하는 모듈의 부작용 등급 집계 |
| 2. Dry-run | DB 스냅샷 위에서 실행 → 변경 예정 레코드 diff, 발송 예정 메일 목록 산출 (메일은 실제 발송 대신 캡처) |
| 3. 승인 게이트 | `write` 이상이 포함되면 diff를 사용자에게 보여주고 승인 요청. `irreversible`은 항목별 개별 승인 |
| 4. 실제 실행 | 실행 전 스냅샷 생성 → 실행 → 모듈 카드의 사후 조건으로 결과 검증 |
| 5. 롤백 | 검증 실패나 예외 발생 시 스냅샷으로 복원 (비가역 항목은 보상 작업 안내) |
| 6. 감사 로그 | 요청·계획 코드·호출 트레이스·diff·승인자·결과를 모두 저장 |

* Guard Proxy: 모든 레거시 호출은 프록시를 거치며, 세션 사용자 범위를 벗어나는 데이터 접근(L9)을 차단
* 리소스 제한: 실행 시간 30초, 레거시 호출 100회, 변경 레코드 50건 상한

### F5. 자가 수정 엔진 (RRSI)

**수정 대상과 금지 대상**

| 수정 가능 (하네스) | 수정 금지 |
| --- | --- |
| 어댑터 코드 (`adapters/*.py`) | 레거시 원본 (`legacy_eworks/*`) |
| 모듈 카드 (파라미터 형식, 사전·사후 조건, 부작용 등급 상향) | 부작용 등급 **하향** (사람 승인 필수) |
| Planner·Router 프롬프트, few-shot 예시 | 런타임 안전장치 코드 |
| 라우팅 임계값 | 모델 가중치 |

**실패 분류 체계**

| 유형 | 예시 | 주 수정 대상 |
| --- | --- | --- |
| E1 파라미터 형식 오류 | `"11월"` → `YYYY-MM` 변환 누락 | 어댑터 정규화 |
| E2 사전 조건 누락 | 세션 없이 호출 → `-1` | 모듈 카드 + 어댑터 |
| E3 잘못된 모듈 선택 | `getAprvLst_old` 호출 | 모듈 카드(폐기 표시) + 라우터 few-shot |
| E4 계획 논리 오류 | 페이지 반복 누락으로 50건만 처리 | 어댑터(페이지 반복 내장) + Planner 프롬프트 |
| E5 의도 오분류 | "취소" 요청을 반려로 해석 | Jev 스키마 설명 + 임계값 |
| E6 레거시 변경 | 파라미터명 `yyyymm` → `stdMonth` 변경 | 모듈 카드 재탐색 + 어댑터 |

**검증 파이프라인**
1. 실패 트레이스를 유형별로 묶음 (동일 유형 N건 이상이면 트리거, 기본 N=3)
2. 수정안 생성: 1회 수정 범위 제한 (파일 2개, 변경 50줄 이내)
3. evolve셋 검증: 해당 실패 케이스 해결 여부
4. Leakage critic: 테스트 케이스 값을 하드코딩했는지 등 과적합 탐지
5. held-out셋 검증: 성능 향상이 노이즈 범위(반복 3회 표준편차)를 넘을 때만 통과, 회귀 0건
6. 운영자 승인 → 반영, 버전 태깅, 롤백 가능

### F6. 스킬 라이브러리 (성공 패턴 축적)

* Plan Path로 성공한 실행 계획 중 유사한 요청이 반복되는 것을 **파라미터화된 스킬**로 일반화해 저장
  * 예: `resubmit_rejected_expenses(month, reason_keyword, append_text)`
* 스킬은 held-out 검증을 통과해야 등록되고, 등록되면 Jev의 판단 후보에 추가 → **다음부터는 LLM 없이 Fast Path로 처리**
* 시간이 지날수록 LLM 호출 비율이 떨어지는 구조이며, 이 추이를 KPI 대시보드에서 확인

## 10. 범위 및 제약사항

* **In Scope**
  * Mock Legacy eWorks 구축 (6개 도메인, 장애 주입기, 버전 업 시뮬레이션)
  * 모듈 자동 탐색·카드 생성·어댑터 자동 생성
  * Jev·LLM 하이브리드 라우팅, Code-as-Action 실행 런타임과 안전장치
  * 하네스 레벨 자가 수정(RRSI), 스킬 라이브러리
  * 운영 UI, KPI 대시보드

* **Out of Scope**
  * 실제 eWorks 레거시·운영 DB 연동
  * 레거시 원본 코드의 자동 수정
  * 모델 가중치 학습·파인튜닝
  * 검증·승인 없는 운영 환경 자동 배포

* **제약사항**
  * Jev는 외부 API라 사내망 반입 정책 확인 필요 (대안: 오픈소스 SemIf 온프렘)
  * Jev 컨텍스트 32K 토큰 제한 → 카탈로그 전체를 넣을 수 없으므로 도메인별 후보 축소(1차 분류 → 2차 모듈 선택) 필요
  * 실행·자가 수정은 샌드박스와 스냅샷 DB에서만 수행
  * 목업 레거시의 현실성은 실제 레거시 경험을 바탕으로 한 특성(L1~L9) 설계로 보완

### 리스크 및 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| LLM이 생성한 코드의 오작동·악용 | 잘못된 데이터 변경 | 정적 검사 + Dry-run + 승인 + 스냅샷 롤백 4중 장치 |
| 숨은 부작용 미탐지 (L8) | 의도치 않은 메일 발송 등 | 호출 그래프 기반 등급 전파, 불확실하면 상위 등급으로 분류 |
| 자가 수정의 과적합 | held-out 성능 저하 | leakage critic, 노이즈 기준 통과 조건, 수정 범위 제한 |
| 목업이 너무 쉬움 | PoC 결과 과대평가 | L1~L9 함정 + 장애 주입으로 난이도 확보, 현업 검토 |
| 카탈로그 증가로 Jev 판단 정확도 하락 | Fast Path 비율 감소 | 계층형 라우팅(도메인 → 모듈), 스킬 우선 매칭 |

## 12. 결정이 필요한 사항

1. Jev 사용 가능 여부 (불가 시 SemIf 온프렘으로 확정)
2. 계획·자가 수정에 쓸 LLM과 사내 반입 가능 여부
3. Mock Legacy 언어: Python으로 단순화(본 문서 기준) vs 실제 레거시와 같은 Java로 구현
4. 자가 수정 반영 승인 정책: 전 건 사람 승인 vs 어댑터 수정은 검증 통과 시 자동 반영
