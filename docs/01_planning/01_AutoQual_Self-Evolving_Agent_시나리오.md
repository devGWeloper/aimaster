### 핵심 사용자 시나리오

**시나리오 1 : PM 후 AutoQual 요청에 대한 멀티 에이전트 자율 협업**

* ID : SC-001

* 상황 : 설비 엔지니어가 장비 PM(정기 보수)을 마치고 장비를 다시 생산에 투입(Up)하려 할 때

* 목표 : 요청 한 줄로 Qual 절차 확인, Seasoning 계획 수립, Qual 결과 판정, Up 전환 승인 요청까지 받는 것

* 사전 조건 : 기준정보·로그분석·레거시DB Agent `active` 상태, CodeAct 샌드박스 런타임·권한 프록시 구성, Jev 판단 게이트 연동, 목업 기준정보 DB·장비 로그·레거시 이력 DB 구축

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 AutoQual 요청 입력 | Super Agent가 요청을 해석하고 Jev가 필요한 Agent를 확률과 함께 선택 | 확신도 높으면 LLM 편성 생략 |
| 2 | - | Super Agent가 하위 Agent 병렬 호출·결과 결합·판정 순서를 Python 실행 계획 코드로 작성 | CodeAct |
| 3 | - | 기준정보 Agent: 장비 모델·PM 종류별 Qual 절차, Spec, 기본 Seasoning 매수 조회 | |
| 4 | - | 로그분석 Agent: PM 후 Leak·Base Pressure 로그, 알람, PM 전 대비 FDC 센서 트레이스 이상 여부 분석 | |
| 5 | - | 레거시DB Agent: 동일 챔버·동일 PM 후 과거 Qual 이력에서 Seasoning 매수별 1차 Pass율 분석 | 약어 컬럼·코드값 해석 포함 |
| 6 | Qual 계획 확인 | Super Agent가 결과를 종합해 Seasoning 매수와 Qual 순서를 근거와 함께 제시 | |
| 7 | Qual 진행 후 판정 요청 | Particle·ER 모니터 결과를 수집해 판정 코드로 Spec 비교 | 판정은 결정적 코드 수행 |
| 8 | Up 전환 승인 | Pass 시 장비 상태 변경 요청을 승인 패널로 전달, 승인 후에만 반영 | L1 Task Loop 종료 |

* 입력 예시

```
[요청] ETCH-07 B챔버 Wet Clean PM 끝났어. AutoQual 진행해줘
```

* 기대 출력

```
[Agent 편성]
- 경로: Jev (기준정보 0.98 / 로그분석 0.95 / 레거시DB 0.91) → 3개 Agent 병렬 실행
- 편성 시간: 0.3s

[Qual 절차] (기준정보 Agent)
- 모델 ETX-300 / PM: WET_CLEAN → 절차 QP-ETX-WC-03
- Leak Check → Seasoning → Particle(≤15ea) → ER Monitor(1,850±5% Å/min, Unif ≤3%)
- 기본 Seasoning: 25매

[챔버 상태] (로그분석 Agent)
- Leak Rate 0.8 mTorr/min (Spec ≤2.0) 정상, PM 후 알람 없음
- RF Reflected Power 초기값 PM 전 대비 +12% → Seasoning 필요량 증가 가능성

[과거 이력] (레거시DB Agent)
- 동일 챔버 Wet Clean 후 최근 8회: 25매 1차 Pass율 50%, 35매 1차 Pass율 100%

[추천] Seasoning 35매 → Particle → ER Monitor
- 근거: RF Reflected 상승 + 과거 25매 Fail 4건 중 3건이 동일 패턴

[판정 - Qual 완료 후]
- Particle 9ea / ER 1,872 Å/min / Unif 2.1% → Qual PASS
- 승인 요청: ETCH-07 B챔버 DOWN → UP 전환
```

* 성공 기준

  * 기준 1: 엔지니어 수작업 대비 Qual 준비·판정 소요시간 70% 이상 단축

  * 기준 2: 과거 Qual 결과 대비 Pass/Fail·재Seasoning 판정 일치율 95% 이상, 무승인 장비 상태 변경 0건

**시나리오 2 : 처음 보는 요청에 대한 Agent 자동 생성 (CodeAct)**

* ID : SC-002

* 상황 : 공정 담당자가 기존 3개 Agent의 능력 범위를 벗어나는 분석을 요청할 때

* 목표 : 개발 요청 없이 시스템이 필요한 Agent를 코드로 직접 만들어 투입하고 결과를 받는 것

* 사전 조건 : Agent Factory 활성화, 공용 스킬 라이브러리 구축, Agent Registry(코드·프롬프트·툴·테스트·지표·버전) 구성, 레거시 DB에 어떤 Agent도 사용하지 않은 부품 교체 이력 테이블 존재

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 분석 요청 입력 | Jev가 "기존 Agent 조합으로 처리 가능한가"를 확률로 판단, 임계값 미만이면 처리 불가 판정 | |
| 2 | - | L2 Grow Loop 진입, LLM이 새 Agent 명세(입력·출력·데이터 소스·재사용할 공용 스킬) 작성 | 사용자에게 생성 중 표시 |
| 3 | - | 레거시 DB 스키마 탐색으로 부품 교체 이력 테이블과 코드값 의미 파악 | 공용 스킬 재사용 우선 |
| 4 | - | Agent 코드와 테스트 코드를 생성해 샌드박스에서 실행, 실패 시 스스로 수정 후 재실행 | 최대 5회·15분 예산 |
| 5 | - | 테스트 통과 시 `probation` 상태로 Registry 등록, 이번 요청 처리에 바로 투입 | |
| 6 | 결과 확인 | 분석 결과와 함께 "신규 생성 Agent 처리" 표시, 운영자에게 승격 검토 요청 | |
| 7 | (운영자) 승격 승인 | 성공 누적 + 승인 시 `active` 승격, 이후 Jev 편성 후보에 자동 포함 | |

* 입력 예시

```
[요청] 지난 분기 ETCH 장비에서 Qual Fail 났던 건들, 교체 부품 사용시간이랑 관계 있는지 분석해줘
```

* 기대 출력

```
[판단]
- Jev: 기존 Agent로 처리 가능 확률 0.22 → Agent 생성

[Agent 생성]
- 신규 Agent: parts_life_agent v0.1 (probation)
- 재사용 스킬: legacy_sql_toolkit, code_value_resolver
- 자가 테스트: 2회차 통과 (1회차 RF 사용시간 단위 오류 → 분→시간 환산 수정)
- 소요시간: 3분 40초

[분석 결과]
- Focus Ring 사용시간별 Qual 1차 Fail율: 0~300h 6% / 300~600h 11% / 600h~ 34%
- 600h 초과 상태 PM 시 1차 Fail 위험 5.7배
- 제안: 600h 초과 챔버는 PM 시 Focus Ring 동시 교체 또는 Seasoning +10매 검토
- 비고: 신규 생성 Agent 처리 결과 (운영자 검토 대기)
```

* 성공 기준

  * 기준 1: 미지원 요청 테스트셋의 70% 이상을 사람 개입 없이 Agent 생성 및 정답 반환

  * 기준 2: 신규 Agent의 공용 스킬 재사용률 50% 이상, 생성 실패 시 예산 내 중단 및 사유 안내

**시나리오 3 : 로그 포맷 변경에 따른 오류 자가 복구 (Self-Healing)**

* ID : SC-003

* 상황 : 장비 SW 업데이트로 FDC 로그 컬럼명과 시간 형식이 바뀐 상태에서 AutoQual 요청이 들어올 때 (장애 주입기로 재현)

* 목표 : 사용자 요청은 끊기지 않고, 로그분석 Agent가 스스로 원인을 찾아 자기 코드를 고쳐 정상화되는 것

* 사전 조건 : 장애 주입기 설정(컬럼명 변경, 시간 형식 변경), 로그분석 Agent 회귀 테스트셋 존재, 이전 정상 버전 Fallback 기능

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | AutoQual 요청 입력 | L1 실행 중 로그분석 Agent 파싱 오류 발생 | |
| 2 | - | 해당 항목을 "확인 불가"로 표시하고 나머지 결과 먼저 응답 | 사용자 대기 없음 |
| 3 | - | L2 Heal Loop 진입, Jev가 오류 유형 분류(포맷 변경/스키마 변경/기준정보 누락/로직 오류/외부 장애/복구 불가) | |
| 4 | - | 신·구 로그 헤더 비교 코드 실행으로 컬럼 매핑·시간 형식 추론, 파서 패치 작성 | CodeAct, 원본 로그 수정 금지 |
| 5 | - | 기존 회귀 테스트 + 신규 포맷 샘플로 검증, 전부 통과 시 새 버전 반영 및 변경 이력 기록 | 하나라도 실패 시 반영 안 함 |
| 6 | 추가 결과 확인 | "확인 불가" 항목 재분석 결과 자동 전달 | |
| 7 | (운영자) 리포트 확인 | 진단 리포트·패치 diff·테스트 결과 열람 | 사후 검토 |

* 입력 예시

```
[요청] CVD-12 A챔버 RF Generator 교체했어. AutoQual 해줘

[실패 로그]
- Agent: log_agent v1.4.1
- 오류: KeyError - 'RF_FWD_PWR'
- 비고: 장애 주입기로 장비 SW v5.2 로그 포맷 적용 (컬럼명 변경, 시간 YYYYMMDDhhmmss → ISO8601)
```

* 기대 출력

```
[1차 응답]
- Qual 절차·과거 이력: 정상 제공
- 챔버 로그 분석: 일시 확인 불가 (로그 형식 변경 감지, 자동 복구 진행 중)

[Self-Healing 리포트 #231]
- 오류 유형: 데이터 포맷 변경 (Jev 0.91)
- 원인: 장비 SW v5.2 업데이트로 FDC 로그 컬럼 7개 변경, 시간 형식 ISO8601
- 조치: SW 버전별 파서 분기 추가 (+38 / -4 lines)
- 검증: 회귀 테스트 48/48 통과 (구 포맷 42 · 신 포맷 6)
- 시도/소요: 2회 / 4분 10초
- 반영: log_agent 1.4.1 → 1.4.2

[추가 응답]
- RF Forward Power 안정화 정상, Reflected 1.2% → Seasoning 기본 매수 유지 권장
```

* 성공 기준

  * 기준 1: 장애 주입 케이스의 70% 이상 자동 복구, 평균 복구 시간 10분 이내

  * 기준 2: 복구 중 사용자 요청 전체 실패 0건, 기존 회귀 테스트를 깨뜨린 패치 반영 0건

**시나리오 4 : Agent 간 코드 중복·성능 저하에 대한 자가 개선 (Self-Evolving)**

* ID : SC-004

* 상황 : 신규 Agent가 여러 개 생성되면서 Agent마다 FDC 파싱·코드값 변환 코드를 따로 보유하고, 로그분석 Agent 응답시간이 늘어난 상태

* 목표 : 사람이 리팩터링하지 않아도 Agent 구조가 스스로 정리되고, 성능 저하 없이 빨라지는 것

* 사전 조건 : L3 Evolve Loop 야간 스케줄 설정, Evolve셋·Held-out셋 분리 준비, Shadow 운영(신·구 버전 결과 비교) 기능, 평가 하네스는 루프 수정 권한 밖에서 고정

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | - | Registry 지표 수집: Agent 간 코드 중복률, 응답시간 추세, 성공률, 사용 빈도 | 일 1회 야간 |
| 2 | - | 이상 감지 및 Jev가 Agent 병합 필요 여부를 확률로 판단 | |
| 3 | - | 개선안 작성: 공용 스킬 추출, Agent 병합, 캐시 도입 등 | CodeAct, 1회 최대 3개 후보 |
| 4 | - | 개선안별 Evolve셋 평가 후 Held-out셋에서 정확도 비하락 확인 | 하락 시 기각 |
| 5 | - | 채택안 Shadow 운영 후 이상 없으면 승격, 변경 계보(Lineage) 기록, 기각 후보도 점수와 함께 진화 아카이브에 보관 | 다음 진화의 출발점으로 재사용 |
| 6 | (운영자) 진화 리포트 확인 | 진화 전후 지표, 채택·기각 사유, 변경 diff 열람 | |

* 입력 예시

```
[Evolve Loop 감지 - 2026-11-12 02:00]
- FDC 파싱 코드 중복: 38% (log_agent, parts_life_agent, chamber_trend_agent)
- log_agent p50 응답시간: 4.1s → 8.7s (+112%)
- chamber_trend_agent ↔ log_agent 기능 중첩: Jev 병합 필요 확률 0.83
```

* 기대 출력

```
[진화 리포트]
- 후보 A 공용 스킬 fdc_toolkit 추출: Evolve셋 +0.0%p / Held-out셋 +0.0%p → 채택
- 후보 B chamber_trend_agent → log_agent 병합: Evolve셋 +1.5%p / Held-out셋 -2.0%p → 기각 (Held-out 하락)
- 후보 C 트레이스 로딩 캐시 도입: 정확도 변화 없음, p50 -41% → 채택

[결과]
- 코드 중복률: 38% → 9%
- log_agent p50 응답시간: 8.7s → 3.9s
- Shadow 24h 통과 → log_agent 1.6.0, parts_life_agent 0.4.0 승격
```

* 성공 기준

  * 기준 1: 진화 후 코드 중복률 50% 이상 감소, 응답시간 30% 이상 단축

  * 기준 2: Held-out셋 정확도가 하락한 진화안 채택 0건, 모든 변경 Lineage 추적 가능

**시나리오 5 : 복구 불가·진화 실패 시 루프 중단 및 롤백 (Loop Engineering)**

* ID : SC-005

* 상황 : 레거시 이력 테이블 이관으로 데이터가 비어 있어 복구가 불가능하거나, 승격된 진화안이 운영 중 특정 장비군에서 이상 결과를 낼 때

* 목표 : Agent가 할 수 없는 일은 예산 안에서 멈추고 사람에게 넘기며, 잘못된 진화는 스스로 되돌리는 것

* 사전 조건 : 루프별 예산(반복 횟수·시간·토큰) 설정, 실패 패치 블랙리스트, Shadow 비교 기반 자동 롤백 기능

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | AutoQual 요청 입력 | 레거시DB Agent 조회 결과 0건 → 사후 검증 실패 → L2 Heal Loop 진입 | |
| 2 | - | 대체 테이블 탐색 패치 반복 시도, 실패한 패치는 블랙리스트 등록 | 동일 시도 반복 방지 |
| 3 | - | Jev가 복구 불가로 재분류하면 예산 소진 전 조기 중단, 운영자에게 진단 리포트 전달 | |
| 4 | 결과 확인 | 이력 보정 없이 기준정보 기본값으로 계획 제시하고 근거 부족을 명시 | 근거 없는 결과 은폐 금지 |
| 5 | - | 별도로, Shadow 비교에서 승격 버전의 판정 불일치 감지 시 이전 버전으로 자동 롤백 | |
| 6 | - | 불일치 샘플을 Held-out셋에 추가해 다음 Evolve Loop에서 재평가 | 실패를 진화 재료로 재활용 |

* 입력 예시

```

**시나리오 6 : 과거 Qual 이력 리플레이 기반 사전 진화 (History Replay Evolving)**

* ID : SC-006

* 상황 : 시스템 도입 직후라 운영 경험은 없지만, 레거시 DB에 3년치 Qual 이력과 당시 장비 로그·부품 교체 이력·엔지니어 조치 기록이 쌓여 있을 때

* 목표 : 운영 투입 전에 과거 이력을 시간 순서대로 재생해, Agent가 "지난 3년의 Qual을 직접 겪은 것처럼" 미리 진화한 상태로 시작하는 것

* 사전 조건 : 레거시 DB Qual 이력·FDC 로그·부품 교체 이력 연결, 시점 고정 데이터 뷰(Time-Travel Guard: 재생 시점 이후 데이터 접근 차단), 리플레이 기간 분할(진화 기간 / 최종 Held-out 기간)

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | (운영자) 리플레이 기간·대상 장비군 지정 | 레거시DB Agent가 과거 Qual 건을 시간순 가상 요청으로 재구성 | 2023-07 ~ 2026-06, 3,000건 |
| 2 | - | Super Agent가 각 건을 실제 요청처럼 처리해 Seasoning 매수 추천·Qual 판정 수행 | 그 시점까지의 데이터만 조회 가능 |
| 3 | - | 당시 실제 결과(최종 Seasoning 매수, 1차 Pass 여부, Fail 항목, 엔지니어 조치)와 비교해 차이를 경험 메모리에 기록 | |
| 4 | - | 구 장비 SW 버전 로그 파싱 실패 → L2 Heal, 반복적으로 필요한 분석 발견 → L2 Grow 자동 발생 | 리플레이 중 Heal·Grow도 함께 진화 |
| 5 | - | 분기 단위로 L3 Evolve 실행: 오차 패턴 분석 → 판단 로직·스킬·Agent 변형 후보 생성 → 다음 분기 데이터로 평가해 채택 | Walk-forward 방식 |
| 6 | - | 진화된 버전으로 다음 분기를 이어서 재생, 마지막 Held-out 기간(2026 상반기)은 진화 없이 최종 평가만 수행 | 과적합 방지 |
| 7 | (운영자) 리플레이 진화 리포트 확인 | 분기별 진화 곡선, 학습된 교훈 목록, 새로 생긴 Agent·스킬, 진화 전후 Held-out 성능 열람 후 운영 투입 승인 | |

* 입력 예시

```

- 대상: ETCH 장비군 (ETX-300, ETX-500), Qual 이력 1,840건
- 진화 기간: 2023-07 ~ 2025-12 (10개 분기, 분기마다 L3 Evolve 1회)

**시나리오 7 : 운영 중 Qual 결과 기반 판단 로직 진화 (Outcome Learning)**

* ID : SC-007

* 상황 : 운영 1개월간 특정 장비 모델의 Wet Clean 후 Agent의 Seasoning 추천을 엔지니어가 반복적으로 올려서 수정(Override)하고, 추천대로 진행한 건은 1차 Qual Fail이 잦은 상태

* 목표 : 사람이 판단 로직을 고치지 않아도, Agent가 현장 결과와 엔지니어 수정 이력을 학습해 추천을 스스로 정확하게 바꾸는 것

* 사전 조건 : 경험 메모리(추천 내용, Override와 사유, 실제 Qual 결과) 축적, 진화에 쓰지 않을 백테스트 기간 데이터 분리, 진화 아카이브 구성

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | (평소처럼) 추천 수정 후 Qual 진행 | 매 건 추천값·Override 값·사유·실제 Qual 결과를 경험 메모리에 기록 | L1 실행 기록이 진화 재료로 축적 |
| 2 | - | L3 Evolve Loop가 장비 모델·PM 종류별 추천 정확도를 분석해 편향 그룹 감지 | Jev가 진화 필요 여부 판단 |
| 3 | - | Override 사유와 Fail 건의 FDC·부품 이력을 비교해 추천 로직이 놓친 변수 분석 | CodeAct |
| 4 | - | 판단 로직 변형 후보를 여러 개 생성(보정 계수 조정, 신규 변수 추가, 조건 분기 추가) | 변이 |
| 5 | - | 각 후보를 진화 기간 데이터로 평가한 뒤, 진화에 쓰지 않은 백테스트 기간에서 1차 Pass율과 Wafer 사용량 비교 | 평가·선택 |
| 6 | (운영자) 진화안 검토·승인 | 승인 시 기준정보 Agent 판단 로직 새 버전 반영, 해당 교훈(Lesson)을 경험 메모리에 등록 | 기각 후보는 아카이브 보관 |
| 7 | 다음 AutoQual 요청 | 진화된 로직으로 추천하고 "어떤 경험에서 바뀌었는지" 근거 함께 표시 | 설명 가능한 진화 |

* 입력 예시

```

- AutoQual 22건 / 엔지니어 Override 9건 (전부 Seasoning 매수 상향, 평균 +10매)
- Override 사유: "RF Reflected 높으면 더 돌려야 함" 5건, "Focus Ring 오래 씀" 3건, 기타 1건
- 추천대로 진행 13건 중 1차 Fail 5건 (Fail 항목: ER Uniformity 4건, Particle 1건)
```

* 기대 출력

```

**시나리오 8 : Super Agent 편성 전략 자기 진화**

* ID : SC-008

* 상황 : Agent가 늘어나면서 Super Agent가 요청마다 필요 이상으로 많은 Agent를 호출하고, 동일 유형 요청에도 매번 LLM이 실행 계획을 새로 작성하는 상태

* 목표 : Super Agent가 자기 편성 방식을 스스로 최적화해, 정확도는 유지하면서 더 적은 호출로 더 빠르게 처리하는 것

* 사전 조건 : 요청 유형별 편성 이력·Agent별 결과 기여도 로그 축적, 편성 템플릿 저장소, Jev 임계값 변경 이력 관리

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | - | L3가 요청 유형별 편성 이력 분석: 호출 Agent별 최종 결과 기여도, LLM 계획 생성 빈도, 사람 확인 빈도 | 일 1회 |
| 2 | - | 기여도 낮은 호출, 반복되는 동일 실행 계획, 과도하게 보수적인 Jev 임계값 감지 | |
| 3 | - | 편성 전략 후보 생성: 불필요 호출 제거, 반복 실행 계획을 편성 템플릿으로 승격, 임계값 재조정 | 변이 |
| 4 | - | 후보별 Evolve셋·Held-out셋 평가(정답률, 응답시간, 호출 수, 사람 확인 빈도) | 정답률 하락 시 기각 |
| 5 | - | 채택안 Shadow 운영 후 승격, 이후 해당 유형 요청은 템플릿으로 LLM 계획 없이 즉시 실행 | |
| 6 | (운영자) 진화 리포트 확인 | 편성 변경 전후 지표 및 채택·기각 사유 열람 | |

* 입력 예시

```
