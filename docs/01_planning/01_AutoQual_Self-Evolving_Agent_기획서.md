### 프로젝트 명

AutoQual Self-Evolving Agent: CodeAct와 Loop Engineering으로 스스로 생성·복구·진화하는 AutoQual 멀티 에이전트

### 배경 및 문제 정의

* AutoQual 업무 개요: 반도체 장비는 PM(정기 보수)·부품 교체·알람으로 Down되면 바로 생산에 돌아갈 수 없음. Leak Check → Seasoning(Dummy Wafer를 반복 투입해 챔버 내벽을 생산 조건으로 복원) → Qual 측정(Particle·ER·Uniformity 모니터 Wafer) → Spec 판정 → Up 승인을 모두 거쳐야 하며, 이 과정이 AutoQual임. Qual이 끝나기 전까지 장비는 생산을 하지 못하므로 **AutoQual 소요시간이 곧 장비 Down Time**. 본 프로젝트가 가정하는 라인(장비 30대·챔버 90개·PM 8종)에서는 챔버당 연 약 11회, 연 약 1,000건의 AutoQual이 발생함

* 현재 상황 (As-Is): Qual 절차·Spec·Seasoning 기준은 기준정보 시스템에, 챔버 상태는 장비 로그(FDC·알람)에, 과거 Qual 이력은 문서화가 부족한 레거시 DB에 흩어져 있어 엔지니어가 세 시스템을 직접 오가며 경험에 의존해 판단함. 기존 자동화·에이전트는 사람이 미리 만든 기능만 수행하며, 새 요청이나 데이터 형식 변경이 생기면 개발자가 직접 기능을 추가·수정해야 함

  Wet Clean PM 1건의 As-Is 흐름 (가상 Fab 기준 추정, Mock 환경 수작업 베이스라인으로 검증 예정)

  | 구간 | 엔지니어가 하는 일 | 소요 | 손실 성격 |
  | --- | --- | --- | --- |
  | Qual 준비 | 기준정보 시스템에서 절차서·Spec·Seasoning 레시피 조회, 절차서 개정 버전 확인 | 20~30분 | 단순 조회 반복 |
  | 챔버 상태 확인 | FDC 화면에서 PM 전후 트레이스를 눈으로 비교, 알람 이력 확인 | 30분 | 숙련도 의존 |
  | 과거 이력 확인 | 레거시 DB를 약어 컬럼·미문서화 코드값과 씨름하며 조회하거나 선임에게 문의. 야간·주말엔 사실상 불가 | 30~60분 | 암묵지 의존 |
  | Seasoning 매수 결정 | 경험과 감으로 결정. 같은 챔버·같은 PM에도 엔지니어별 25~45매 편차 | - | 판단 편차 |
  | Seasoning·측정 | 25매 Seasoning 약 1.5시간 + Particle·ER 측정 약 1시간 | 약 2.5시간 | 필수 공정 |
  | 1차 Fail 시 | 원인 분석(로그·이력 재조회) 1~2시간 + 재Seasoning·재측정 1.5~2시간 | 3~4시간 | 판단 실패 비용 |
  | Up 승인 | 결과 정리·보고·승인 요청 | 20분 | 수작업 |

  → 꼭 필요한 공정 시간은 약 2.5시간인데, 판단 준비와 1차 Fail 재작업이 붙으면 7~8시간이 됨. **Down Time의 절반 이상이 장비가 아니라 '판단'에서 생김**

* Pain Point (가상 Fab 규모 기준 추정치, Mock 환경 베이스라인으로 검증 예정):

  1. **판단 실패 한 번 = 장비 수 시간 추가 Down**: 1차 Pass율을 약 70%로 가정하면 연 약 300건이 재작업이고, 건당 3~4시간씩 연 약 1,000 챔버·시간이 추가로 멈춤(챔버 1개를 40일 넘게 세워두는 규모). 원인을 모른 채 "일단 더 돌려보기"로 대응하면 2·3차 Fail까지 이어짐
  2. **핵심 판단이 숙련자 머릿속에만 있음**: Seasoning 매수와 "어떤 신호가 위험한지"는 문서가 아니라 사람의 경험에 있음. 엔지니어별 판단 편차, 숙련자 이동·퇴사 시 노하우 유실, 확인할 사람이 없는 야간·주말 교대조의 과잉 Seasoning(Dummy Wafer·장비 시간 낭비) 또는 무리한 진행이 반복됨. 판단 준비만 건당 1.5~2시간, 연 1,500~2,000 엔지니어 시간
  3. **3년치 결과가 쌓여도 아무것도 배우지 않음**: 3,000건의 Qual 결과와 엔지니어 조치가 레거시 DB에 있지만 해석이 어려워 방치되고, 기준정보의 기본 Seasoning 매수는 장비 도입 때 정한 값이 수년째 그대로임. 같은 Fail 패턴(예: 특정 모델 Wet Clean 후 ER Uniformity Fail)이 반복돼도 시스템 판단은 바뀌지 않으며, 바뀌는 것은 개인의 경험뿐이고 그마저 공유되지 않음
  4. **자동화는 조용히 깨지고, 더 나쁘게는 조용히 틀림**: 장비 SW 업데이트(로그 컬럼·시간 형식 변경), 레거시 테이블 이관, 단위 변경(mTorr → Torr)이 생기면 기존 자동화는 멈추거나 에러 없이 틀린 값을 냄. 가장 위험한 것은 **에러 없는 오판**으로, Leak Rate가 1/1,000로 읽혀 정상처럼 보이면 비정상 챔버가 Up되고 제품 Wafer 불량·Lot Scrap으로 이어질 수 있음. 이 손실은 Qual 시간 손실보다 몇 자릿수 큼
  5. **새 질문 하나에 수 주, 한 번 만든 기능은 쌓이기만 함**: "Fail이 부품 사용시간과 관계있나?" 같은 분석은 기존 기능 밖이라 IT 개발 요청 → 우선순위 대기 → 개발 → 배포까지 수 주가 걸리고, 그동안 엔지니어는 엑셀로 수작업함. 반대로 한 번 만든 기능은 아무도 지우지 않아 중복·미사용 코드가 쌓이고 유지보수 비용과 응답시간이 계속 늘어남

* 기존 접근이 이 문제를 못 푼 이유:

  | 접근 | 한계 |
  | --- | --- |
  | 룰 기반 자동화·스크립트 | 사람이 정한 규칙만 수행. 로그 포맷·스키마가 바뀌면 깨지고, 결과가 쌓여도 규칙은 그대로 |
  | 대시보드·BI | 데이터를 보여줄 뿐 판단은 여전히 사람 몫. 세 시스템 결합과 레거시 코드 해석도 사람 몫 |
  | RAG 챗봇 | 문서 검색은 되지만 정형 데이터 계산·시점 조건 조회에 약하고 다른 장비 사례가 섞임. 판단 로직을 개선하지 못함 |
  | 고정 기능 멀티 에이전트 (JSON 툴 호출) | 미리 만든 툴 안에서만 동작. 새 요청·포맷 변경에는 개발자가 필요하고 기능이 늘수록 중복·미사용이 쌓임 |

  → 데이터를 연결하는 것만으로는 부족함. 이 프로젝트의 핵심은 **판단 로직 자체가 현장 결과로 계속 갱신되고, 환경 변화에 스스로 적응하며, 필요한 기능은 스스로 만들고 불필요해진 기능은 스스로 정리하는 구조**를 만드는 것

  | ⑤ 새 질문에 수 주 / 기능은 쌓이기만 | CodeAct Grow로 수 분 내 Agent 생성, Evolve로 중복 통합, Retire로 불필요 Agent 폐기 | SC-002, SC-004, SC-009 | 생성 성공률 70%, 중복률 50%↓, 미사용 Agent 잔존 0개 |

* 기회 요인:
  * JSON 툴 호출 대신 실행 가능한 코드를 행동으로 쓰는 CodeAct 방식이 확산되어, 에이전트가 기능을 고르는 수준을 넘어 기능(Agent)을 직접 만들고 고치는 것이 가능해짐
  * 에이전트가 자기 코드·프롬프트·툴을 수정하고 평가해 더 나은 버전만 채택하는 Self-Evolving(Recursive Self-Improvement) 연구가 실용 단계에 진입. Sakana AI의 Darwin Gödel Machine은 코딩 에이전트가 자기 코드를 변형·평가하고 후보를 아카이브에 쌓아가며 SWE-bench 성능을 20%에서 50%로 끌어올렸고, Google DeepMind의 AlphaEvolve는 LLM 코드 변형과 자동 평가를 결합한 진화 탐색으로 실제 알고리즘을 개선함
  * 프롬프트 설계보다 "어떤 루프를 언제 돌리고 언제 멈출지"를 설계하는 Loop Engineering이 자율 에이전트 품질의 핵심으로 부각
  * 2026년 9월 TypeSafe AI가 텍스트 대신 선택·점수·예/아니오에 보정된 확률로 답하는 의사결정 모델(Jev)을 공개해, 루프 안에서 반복되는 분기 판단을 빠르고 저렴하게 처리 가능

### 목표 사용자 (Target User)

* 설비 엔지니어: PM 후 AutoQual을 수행하고 장비 Up 여부를 판정하는 인력
* 공정/Qual 담당자: Qual Spec을 관리하고 Qual 이력·Fail 원인을 분석하는 인력
* 에이전트 운영자: 에이전트 품질을 관리하며 Agent 생성·복구·진화 결과를 검토·승인하는 AI 엔지니어

### 프로젝트 목표

* 정성적 목표

  * 목표 1: 요청 하나로 Super Agent가 기준정보·로그분석·레거시DB Agent를 스스로 편성해 AutoQual 업무를 완료하는 멀티 에이전트 구조 확립

  * 목표 2: 처음 보는 요청에 필요한 Agent를 CodeAct로 직접 생성하고, 오류 발생 시 스스로 복구하며, 중복·성능 저하를 스스로 개선하고, 오래 쓰이지 않거나 대체되어 불필요해진 Agent는 안전하게 폐기하는 Self-Evolving 체계 구축

  * 목표 3: 레거시 DB에 쌓인 과거 Qual 이력을 시간순으로 재생해 운영 전에 미리 진화시키고, 운영 중에는 실제 Qual 결과와 엔지니어 수정 이력을 학습해 AutoQual 판단 로직과 Super Agent 편성 전략까지 쓸수록 정확해지는 이력 기반 진화 구조 확립

  * 목표 4: 실행(Task)·복구/생성(Heal/Grow)·진화(Evolve) 3중 루프에 트리거·종료 조건·예산·검증 게이트를 설계해 폭주 없이 자율 동작하는 Loop Engineering 확립

  * 목표 5: 장비 상태 변경 승인, 샌드박스 실행, Held-out 검증, 자동 롤백으로 안전한 자율성 확보

  * 목표 6: CodeAct, Self-Evolving, Loop Engineering, 의사결정 모델(Jev) 기반 에이전트 기술 내재화

| 무승인 장비 상태 변경 | 0건 | 사람 승인 없이 장비 상태(Down→Up)가 반영된 건수 | - |

### 핵심 기능 정의

1. Mock AutoQual 환경: 장비 30대·챔버 90개·PM 종류 8개의 기준정보 DB(Qual 절차·Spec·Seasoning 레시피 매핑), PM 전후 FDC 센서 트레이스·알람 로그와 부품 교체 이력, 3년치 Qual 이력 3,000건(엔지니어 조치 기록 포함)의 레거시 DB(약어 컬럼, 문서화 안 된 코드값, 폐기 테이블 잔존, 기간별 장비 SW 버전에 따른 로그 포맷 상이)로 구성. 장애 주입기로 로그 포맷 변경, DB 컬럼 변경, 타임아웃, 단위 변경 등을 재현

2. Super Agent 및 메인 Agent: Super Agent가 요청을 해석해 하위 Agent를 편성하고 결과를 종합·판정. 기준정보 Agent(Qual 절차·Spec·Seasoning 기준 조회), 로그분석 Agent(PM 전후 센서 트레이스·알람 이상 탐지), 레거시DB Agent(과거 Qual 이력·재시도 패턴 분석) 3개로 시작하며, 모든 Agent는 코드·프롬프트·툴·테스트·지표·버전을 묶은 Genome 단위로 Agent Registry에 저장되어 생성·복구·진화의 대상이 됨

3. CodeAct 실행 런타임 및 Agent Factory: 모든 Agent는 Python 코드를 행동으로 작성해 샌드박스에서 실행(일상 실행). 기존 Agent로 처리할 수 없는 요청이 오면 Agent Factory가 새 Agent의 명세·코드·테스트를 직접 작성하고 자가 테스트 통과 시 probation 상태로 투입(Agent 생성). 오류·성능 저하 시 패치·리팩터링 코드를 작성(자기 수정). 오래 쓰이지 않았거나 다른 Agent가 기능을 흡수해 불필요해진 Agent는 의존성 분석·대체 경로 검증 코드를 실행한 뒤 `deprecated`(14일 유예, 호출은 대체 Agent로 리다이렉트) → 운영자 승인 후 `retired`(편성·Heal·회귀 대상에서 제거, Genome은 아카이브 보관·복원 가능)로 정리(Agent 폐기). Agent 생명주기는 `probation` → `active` → `deprecated` → `retired`로 관리하고 기본 Agent(Super·기준정보·로그분석·레거시DB)는 폐기 대상에서 제외. 허용 모듈 외 import 차단, 기본 읽기 전용 권한 프록시, 정적 검사, 감사 로그 적용

4. Self-Evolving 엔진: 진화 대상을 5계층으로 정의함. ① 파라미터·프롬프트(Jev 임계값, Seasoning 보정 계수, Agent 프롬프트) ② 스킬(성공한 CodeAct 코드를 파라미터화한 공용 함수) ③ Agent 코드(파서·SQL·판정 로직) ④ Agent 구성(생성·병합·분리·폐기) ⑤ Super Agent 편성 전략. 진화는 Grow(처리 불가 요청 → 새 Agent 생성), Heal(실행 오류·사후 검증 실패 → 오류 유형 분류 → 자기 코드 패치 → 회귀 테스트, 복구 중 이전 버전 Fallback), Evolve(코드 중복·기능 중첩·응답시간 증가·판단 정확도 저하·미사용 감지 → 개선)의 3가지 트리거로 시작되며, 공통적으로 "변이(LLM이 개선 후보 코드를 여러 개 생성) → 평가(루프 밖에서 고정된 평가 하네스로 채점) → 선택(Evolve셋 개선 + Held-out셋 비하락 시에만 채택) → 보관(채택·기각 후보를 모두 진화 아카이브에 저장해 다음 진화의 출발점으로 재사용)" 사이클을 따름. ④ Agent 구성 계층의 폐기(Retire)는 잘못 지우면 기능이 사라지므로 별도 안전 절차(장기 미사용·대체 감지 → 직접·간접 의존성 분석 → 대체 Agent로 회귀·실제 요청 재실행 검증 → 테스트 이관 → 유예 → 사람 승인 → 아카이브 보관)를 따르며, 이후 유사 요청이 오면 Agent Factory가 새로 만들기 전에 아카이브에서 복원을 먼저 검토. 채택안은 승격 후에도 직전 버전과 Shadow 병행하며 이상 시 공용 스킬 의존 Agent까지 원자적으로 자동 롤백, 모든 변경은 Lineage로 추적하며 원본 데이터·레거시 시스템은 수정하지 않음

5. 이력 리플레이 진화(History Replay Evolving): 레거시 DB의 과거 Qual 이력(3년치)을 당시 장비 로그·부품 교체 이력·엔지니어 조치와 함께 시간순 가상 요청으로 재구성해 Agent가 실제 요청처럼 처리하게 하고, 당시 실제 결과와의 차이를 학습 재료로 사용. 분기 단위로 L3 Evolve를 실행해 다음 분기 데이터로 평가하는 Walk-forward 방식으로 진화하며, 최근 6개월은 Held-out 기간으로 남겨 최종 평가에만 사용. 재생 시점 이후 데이터 조회를 차단하는 Time-Travel Guard로 미래 정보 누출을 방지. 리플레이 중 구 장비 SW 로그 파싱 실패(Heal)나 반복적으로 필요한 분석(Grow)도 자연스럽게 발생해, 운영 투입 전에 판단 로직·스킬·Agent 구성이 지난 이력을 모두 겪은 상태로 진화함(Cold Start 해소)

6. 경험 메모리 및 판단 진화(Outcome Learning): 운영 중 모든 AutoQual 건의 추천 내용, 엔지니어 수정(Override)과 사유, 실제 Qual 결과(1차 Pass 여부, 최종 Seasoning 매수, Fail 항목)를 경험 메모리에 축적. 성공한 실행은 스킬로, 실패·Override는 교훈(Lesson)으로 저장해 유사 요청 시 Agent가 참고. L3 Evolve Loop가 장비 모델·PM 종류별 추천 편향(예: 특정 모델 Wet Clean 후 Seasoning 과소 추천)을 감지하면 판단 로직 변형 후보를 생성하고, 진화에 쓰지 않은 기간 데이터로 백테스트해 1차 Pass율이 개선된 경우에만 채택. 쓸수록 현장 결과에 맞춰 Qual 판단이 정확해지는 구조

7. Super Agent 자기 진화: 요청 유형별 편성 이력과 결과를 분석해 결과에 기여하지 않는 Agent 호출 제거, 자주 함께 쓰이는 Agent 조합과 실행 계획 코드를 편성 템플릿으로 승격(다음부터 LLM 계획 없이 바로 실행), Jev 임계값을 정확도·비용·사람 확인 빈도 기준으로 재조정. 편성 전략 변경도 4번과 같은 변이·평가·선택·보관 사이클과 Held-out 검증을 거침

8. 3중 루프(Loop Engineering): L1 Task Loop(요청 단위, 계획→코드→실행→관찰, 목표 충족 시 종료), L2 Heal/Grow Loop(이벤트 단위, 진단→패치·생성→테스트, 최대 5회·15분), L3 Evolve Loop(운영 중 일 단위, 이력 리플레이 시 분기 단위, 지표·경험 메모리 분석→개선 후보 생성→평가→승격)로 구성. 과거 이력 리플레이와 L1의 실행 기록·실제 Qual 결과가 L3의 진화 재료가 되고, L3의 결과가 다시 L1의 실행 방식을 바꾸는 순환 구조. 루프별 트리거·종료 조건·예산·실패 시 처리·사람 개입 지점을 명세하고, 실패한 패치 블랙리스트로 동일 시도 반복을 막으며, 평가 하네스는 루프 수정 권한 밖에서 고정해 자기 평가 조작을 방지

9. Jev 판단 게이트: 코드 작성·계획은 LLM이, 루프 안에서 반복되는 짧은 분기 판단은 Jev가 담당. Agent 편성(복수 선택), 기존 Agent로 처리 가능 여부(예/아니오 확률), 오류 유형 분류(선택), 루프 종료 여부(점수), Agent 병합·진화·폐기 필요 여부(예/아니오 확률)에 사용하며, 보정된 확률을 임계값으로 써서 자율 처리·LLM 에스컬레이션·사람 확인을 구분. Spec 판정·권한 체크는 결정적 코드가 수행

10. 운영 UI: 채팅 요청, 실시간 Agent 편성 그래프, CodeAct 실행 코드·루프 트레이스, 장비 상태 변경 승인 패널, Self-Healing·진화 리포트, 이력 리플레이 진화 곡선, 진화 아카이브(채택·기각·폐기 후보와 점수), Agent 생명주기(probation·active·deprecated·retired) 및 Lineage 뷰 제공

### 기대 효과

* 업무 효율화: Qual 준비·판정·Fail 분석 자동화로 건당 1.5~2시간의 판단 준비를 30분 이내로 단축, 1차 Pass율 70% → 85% 달성 시 연 재작업 약 150건·약 500 챔버·시간의 Down Time 감소(추정), 새 분석 요청을 개발 요청 없이 Agent 자동 생성으로 수 주 → 수 분 내 대응

* 품질 향상: 개인 경험에 의존하던 Seasoning 매수·판정을 이력 기반으로 표준화하고, 과거 이력 리플레이로 첫날부터 수년치 Qual 경험이 반영된 상태로 운영을 시작하며, 실제 Qual 결과를 학습해 쓸수록 1차 Pass율이 높아지는 구조 확보, 로그·스키마 변경에도 자가 복구로 무중단 운영하고 사후 검증으로 에러 없는 오판(오판 Up에 따른 Lot Scrap 위험)까지 차단, 진화 과정에서 Held-out 검증으로 성능 퇴화 방지

* 비용 절감: 과잉 Seasoning에 따른 Dummy Wafer·장비 시간 절감, 에이전트 기능 개발·유지보수 공수 감소, 중복 통합·불필요 Agent 폐기로 회귀 테스트·Heal 대상 코드 축소, 반복 분기 판단을 Jev로 처리해 LLM 호출 비용 절감

### 범위 및 제약사항

* In Scope: Mock AutoQual 환경(기준정보 DB·장비 로그·레거시 DB·장애 주입기) 구축, Super Agent 및 기준정보·로그분석·레거시DB Agent, CodeAct 실행 런타임과 Agent Factory, Self-Evolving 엔진(Grow·Heal·Evolve, 5계층 진화 대상, Agent 폐기(Retire)와 생명주기 관리, 진화 아카이브), 과거 Qual 이력 리플레이 진화(Time-Travel Guard 포함), 경험 메모리 및 판단 진화, Super Agent 편성 전략 진화, 3중 루프와 예산·검증 게이트, Jev 판단 게이트, Agent Registry 및 Lineage 관리, 운영 UI

* Out of Scope: 실제 장비·MES·EES 연동, 장비 직접 제어(레시피 투입·상태 변경 자동 실행), 원본 데이터·레거시 시스템 수정, 모델 가중치 학습·파인튜닝

* 제약사항: 사내 실데이터 사용 불가로 목업 데이터 기반 구축(현실성은 실제 AutoQual 업무 경험 기반 설계로 보완), Jev는 외부 API로 사내망 반입 정책 확인 필요(대안: SemIf 온프렘 구성 또는 소형 분류 모델 대체), 생성·수정 코드 실행은 샌드박스에서만 수행, 장비 상태 변경과 Agent 정식 승격은 사람 승인 유지
