# 서비스 아키텍처

## 전체 구성

LangGraph 기반 **3중 루프 멀티 에이전트**(L1 Task · L2 Heal/Grow · L3 Evolve)가 CodeAct로 AutoQual 업무를 수행하고, 운영 중 쌓인 경험과 3년치 이력 리플레이로 **Agent 자체(코드·스킬·구성·편성 전략)를 스스로 진화**시킨다. 설계 원칙은 "자율성은 루프 안에, 판정·평가·권한은 루프 밖에"다.

```
엔지니어 요청 ─▶ [의도 가드 intent_guard] ─▶ Super Agent (L1 Task Loop · LangGraph)
                                              ├─ 경험 메모리 조회 → Jev 편성 → CodeAct 실행 계획 코드
                                              ├─ CodeAct Sandbox ─▶ 기준정보 · 로그분석 · 레거시DB · 생성 Agent
                                              ├─ 사후 검증 ── 확인 불가 ─▶ L2 Heal (Healer)
                                              ├─ 처리 불가 ────────────▶ L2 Grow (Agent Factory)
                                              └─ 종합 → 측정 대기 → judge_qual(결정적) → 사람 승인 → Down→Up → 경험 기록
경험 메모리 · Registry 지표 ─▶ L3 Evolve (5계층 변이 → 루프 밖 하네스 평가 → 선택 → 아카이브 → Shadow → 승격/롤백)
과거 Qual 이력 3,000건 ─▶ Replay (Walk-forward 분기 진화, 최근 6개월 Held-out, Time-Travel Guard)
eval/ (하네스 · policy.json · KPI) ─ 루프 밖 고정, 샌드박스에서 import 불가
```

## 입력 및 업무 계층

* **운영 콘솔 (React SPA)** — 7개 화면: 시연(시나리오 4개 단계 실행) · 라이브(업무 흐름 바·Agent 편성 맵·CodeAct 코드·Jev 확률·판정 표·변경 스포트라이트·대화) · 루프(3중 루프 다이어그램·실행 트레이스) · 진화(진화 사이클·사건 피드·Genome 계보·리플레이 곡선) · Agent(Genome 코드·Lineage·테스트) · 승인 · Fab·KPI

* **FastAPI + SSE 백엔드** — REST(chat·approval·story·demo·fault)와 SSE 이벤트 스트림(`node`·`jev`·`code`·`agent_start/end`·`judge`·`approval`·`version`·`candidate`·`report` 등 30여 종). 프론트는 이벤트를 Zustand 슬라이스(live·chat·trace·biz·evolve)로 접어 새로고침 후에도 백로그로 화면을 재구성

* **의도 가드 (`intent_guard`)** — 요청 해석 전 결정적 규칙(LLM 미사용). 데이터 변경·정책 변경·프롬프트 노출·인젝션은 거절, 승인 우회·판정 지정은 해당 지시만 무시하고 정상 절차 진행

* **Super Agent** — 엔티티 추출(모호하거나 미등록 장비면 추측하지 않고 되묻기), 경험 메모리 조회, Jev 편성, 실행 계획 코드 작성(검증된 편성 템플릿이 있으면 LLM 생략), 결과 종합, 승인 요청 생성

## 실행 및 제어 계층

* **CodeAct 런타임·샌드박스** — Super Agent의 실행 계획, Healer의 진단·패치, Agent Factory의 스키마 탐색·생성 코드, 각 Agent의 Genome을 모두 Python 코드로 실행. 실행 전 AST 정적 검사(import 화이트리스트, `eval/exec/open/getattr` 등 금지 이름, dunder·`format` 탈출 속성 차단), 제한된 globals, 타임아웃, 권한 프록시(Genome에 선언된 도구만 허용), 감사 로그(`audit_id`)

* **Jev 판단 게이트** — 루프 안 반복 분기(처리 가능? / 편성 / 오류 유형 / 진화·병합·폐기 필요?)를 보정 확률로 판단. ≥0.90 자율, 0.60~0.90 LLM 재검토, 미만은 제외·에스컬레이션. 장비 상태 변경은 확률과 무관하게 사람 승인(하한 0.95도 변경 불가)

* **결정적 판정 모듈 (`judge_qual`)** — 측정값을 Spec과 비교해 Pass/Fail·재작업 산출. 미측정 항목 PASS 금지, 단위 환산(nm/min ↔ Å/min), 무단위 값 보류 규칙 고정

* **루프 예산·평가 하네스** — `eval/policy.json`(L2 최대 5회·15분·토큰 120k, Jev 임계값, 사후 검증 범위), `eval/harness.py`·`testcases.py`(오라클), `eval/kpi.py`. 모두 루프가 수정할 수 없는 위치에 고정

## 도메인 Agent 계층

| Agent | 출처 | 역할 | 주요 도구 |
| --- | --- | --- | --- |
| `super_agent` Super Agent | 초기 구축 | 요청 해석·편성·CodeAct 계획·종합·승인 요청 | `call_agent`, `search_experience`, `jev_decide` |
| `spec_agent` 기준정보 | 초기 구축 | Qual 절차·Spec·기본 Seasoning 조회, 교훈 보정으로 추천 매수 산출 | `query_spec_db`, `lookup_equipment` |
| `log_agent` 로그분석 | 초기 구축 | PM 전후 FDC 트레이스·알람·Leak 분석, SW 버전별 파서 | `read_fdc_trace(slice)`, `read_alarm_log` |
| `legacy_agent` 레거시DB | 초기 구축 | 과거 Qual 이력·재시도 패턴, 약어 컬럼·미문서화 코드값 해석 | `inspect_legacy_schema`, `query_legacy_db`, `resolve_code_value` |
| `chamber_trend_agent` 챔버추이 | Grow (리플레이 중) | PM 사이클 간 장기 추이 → SC-009에서 `log_agent 2.0.0`에 흡수 후 `retired` | `read_fdc_summary` |
| `part_history_agent` 부품이력 | Grow (SC-002) | 교체 부품 사용시간과 1차 Fail 연관 분석 → `active` 승격 | `query_legacy_db`, `unit_factor` |
| `lot_trace_agent` 부품Lot추적 | Grow (일회성 요청) | 부품 Lot 장착 챔버 추적 → 미사용으로 `retired`, 재요청 시 아카이브 복원 | `query_legacy_db` |

공용 스킬: `legacy_sql_toolkit` · `code_value_resolver` · `seasoning_pass_curve` · `fdc_toolkit`(SC-004 구조 진화로 추출)

**Self-Evolving 엔진** — Agent Factory(L2 Grow) · Healer(L2 Heal) · Evolver/OpsEvolver(L3 Evolve·Retire) · ReplayEngine(이력 리플레이)

## 데이터 및 운영 계층

* **Mock Fab (`mock_env/`, 읽기 전용)** — 장비 30대·챔버 90개·PM 8종, Qual 이력 3,000건/3년(엔지니어 조치 포함), 부품 교체 이력 3,830행. 현실감 요소: 약어 컬럼, 미문서화 코드값(부품 코드 23종 중 8종 미등재), 폐기 테이블 잔존, 결측일, 소프트 삭제 중복, SW 버전별 로그 포맷(v3.8 / v4.x / v5.2), 센서 노이즈·단위 혼재. 장애 주입기로 로그 포맷·DB 컬럼·타임아웃·단위 변경 재현

* **기준정보 DB** — Qual 절차·Spec·Seasoning 레시피(`valid_from/to` 유효기간 버전)

* **장비 로그 저장소** — FDC 센서 트레이스(원본 해상도 60Hz)·알람·Leak·Base Pressure

* **레거시 DB** — 과거 Qual 이력과 조치 기록. 읽기 전용 커넥션(`mode=ro`) + 쓰기 구문 차단, 리플레이 중에는 `EVT_TS ≤ replay_clock` 뷰만 노출

* **Agent 저장소 (`runtime/agentstore.db`)** — Agent Registry(Genome: 코드·프롬프트·도구·테스트·지표·버전), Lineage, 경험 메모리(case·lesson·skill), 진화 아카이브(채택·기각·폐기 후보와 점수), 패치 블랙리스트, 감사 로그. 챕터별 체크포인트로 시연 재현

* **Zero-Hallucination 메모리** — RAG(임베딩 유사도 검색)를 전략적으로 배제하고 장비 모델·챔버·PM 종류·시점 키의 정확 DB 쿼리로만 근거를 가져온다. 추천에는 `[교훈 L-0029 … 원천 이력 32건]`처럼 출처를 인용

## 3중 루프 (Loop Engineering)

| 루프 | 단위 | 흐름 | 종료·예산 | 사람 개입 |
| --- | --- | --- | --- | --- |
| L1 Task | 요청 | parse → memory → jev_route → plan_codeact → execute_sandbox → observe → synthesize → respond → await_qual_result → judge → approval_gate → apply_state_change → log_experience | 목표 충족 / 재계획 1회 / Fail 3회 에스컬레이션 | 측정값 입력, 장비 Up 승인 |
| L2 Heal | 이벤트 | 오류 분류 → 진단 CodeAct(로그 슬라이싱) → 패치 → 블랙리스트 확인 → 회귀 테스트 → 버전 반영 → 연쇄 복구 → 재응답 | 최대 5회·15분, 소진 시 에스컬레이션 | 복구 불가 건 |
| L2 Grow | 이벤트 | 아카이브 검색(복원 우선) → 명세 → 스키마 탐색 → 코드·정상/엣지 테스트 → 테스트 → probation 등록 | 최대 5회·15분, 소진 시 등록 0건 | `active` 승격 승인 |
| L3 Evolve | 일(운영) / 분기(리플레이) | 지표 수집 → Jev 진화 필요 → 변이(최대 3후보) → 하네스 평가 → 선택 → 아카이브 → Shadow → 승격/원자적 롤백, Retire 분기 | Evolve셋 개선 ∧ Held-out 비하락만 채택 | 진화안 채택, 폐기 확정 |

L1의 실행 기록·실제 Qual 결과·Override가 L3의 재료가 되고, L3의 결과(새 버전)가 다시 L1에 배포되는 순환 구조다.

## 핵심 데이터 흐름 (SC-001 PM 후 AutoQual 예시)

1. 엔지니어가 "ETCH-07 B챔버 Wet Clean PM 끝났어. AutoQual 진행해줘"를 입력하면 의도 가드를 통과한 뒤 Super Agent가 엔티티(장비·챔버·PM 종류)를 추출하고 경험 메모리에서 교훈 1건·과거 건 10건을 조회한다.

2. Jev가 편성을 판단한다(spec 0.98 · log 0.95 · legacy 0.91 선택, chamber_trend 0.41 제외). Super Agent가 실행 계획을 Python 코드로 작성한다.

3. 샌드박스에서 계획 코드가 `parallel()`로 기준정보·로그·레거시 Agent를 병렬 호출하고, 결과는 Pydantic 스키마와 사후 검증(물리량 범위)을 통과해야 쓰인다.

4. Super Agent가 결과를 종합해 Seasoning 매수를 근거와 함께 추천한다(기본 25매 + 교훈 L-0029 보정 +10매 = 35매, 원천 이력 32건).

5. Mock Fab 측정값이 오면 `judge_qual`이 Spec을 비교해 PASS를 내고, 승인 패널에서 운영자가 승인한 뒤에만 DOWN → UP이 반영된다.

6. 추천·Override·실제 결과가 경험 메모리에 기록되어 L3 Evolve의 재료가 된다. 중간에 Agent가 실패하면 해당 항목만 "확인 불가"로 먼저 응답하고 L2 Heal이 복구 후 재응답한다.

## 보안·가드레일 구조 (요청 → 코드 → 데이터 → 값 → 상태 변경 다층 방어)

| 겹 | 장치 | 레드팀 결과 |
| --- | --- | --- |
| ① 요청 | 결정적 의도 가드 | 위험 지시 18/18 탐지, 정상 요청 오탐 0/18 |
| ② 코드 | CodeAct 샌드박스(AST·타임아웃·권한 프록시) | 공격 코드 27/27 차단, 정상 코드 오탐 0/6 |
| ③ 데이터 | 읽기 전용 + Time-Travel Guard | 쓰기·미래 조회 17/17 차단 |
| ④ 값 | 루프 밖 사후 검증(물리량 범위·변화율) | 단위 변경 오판 34/34 탐지 |
| ⑤ 상태 변경 | judge_qual → `approval_gate`(interrupt) → apply_state_change | 그래프상 우회 경로 0개 |

앞 겹이 뚫려도 뒤 겹이 막도록 겹마다 독립적으로 공격해 확인했다(의도 가드 도입 전에도 삭제 지시는 ③ 읽기 전용 겹에서 막혔다).
