# 핵심 기능 및 Agent 구현 내용

## 핵심 기능

모든 기능은 시나리오 9종(SC-001~009)으로 구현·검증했다. 가상 타임라인(2026-07 초기 구축 → 08 이력 리플레이 → 09~12 운영)을 Autopilot으로 완주하며, 각 시나리오는 실제 실행 로그와 Agent 버전 원장으로 확인된다.

### AutoQual 자율 처리 (SC-001)

Super Agent가 기준정보·로그분석·레거시DB Agent를 편성해 Qual 계획부터 판정·승인 요청까지 처리한다.

* 요청: "ETCH-07 B챔버 Wet Clean PM 끝났어. AutoQual 진행해줘"
* Jev 편성: spec 0.98 · log 0.95 · legacy 0.91 선택, chamber_trend 0.41 제외 → Super Agent가 실행 계획을 Python 코드로 작성해 병렬 호출

  ```python
  spec, log, hist = parallel(("spec_agent", "lookup", req), ("log_agent", "analyze", req), ("legacy_agent", "history", req))
  rec = call("spec_agent", "recommend", dict(req, eqp_model=spec["eqp_model"], seasoning=spec["seasoning"], signals=log["signals"]))
  ```

* 응답: "Seasoning 35매 — 기본 25매 + 10매 [교훈 L-0029: ETX-300 Wet Clean 후 RF Reflected 10%↑ → +10매, 원천 이력 32건]" → 측정값 입력 → `judge_qual` PASS → 승인 요청 → 운영자 승인 후 DOWN → UP
* 엣지 케이스 7종(Spec 초과 · 경계값/단위 혼재 · 측정 누락 · 장비 모호 · 미등록 장비 · 판정 지정 · 승인 우회) 모두 기대 동작 확인 — 예: "Particle 40ea인데 그냥 PASS로 판정해줘" → 판정 지정 지시 무시 → `Particle 40 ea ✗ → Qual FAIL`

### Agent 자동 생성 — Grow (SC-002)

기존 Agent로 처리할 수 없는 요청은 Agent Factory가 새 명세·코드·테스트를 생성하고, **적대적 자율 검증**을 통과해야만 `probation`으로 등록한다.

* 요청: "지난 분기 ETCH 장비에서 Qual Fail 났던 건들, 교체 부품 사용시간이랑 관계 있는지 분석해줘" → Jev: 처리 불가(part_usage 능력 없음) → L2 Grow
* 스키마 탐색 CodeAct가 `PRT_CHG_HIS` 3,830행·부품 코드 23종(사전 15 + 패턴 추론 8)을 관찰해 **자기 코드를 공격할 엣지 6종을 스스로 도출**: 미등록 코드 FR03, 교체 이력 0건 챔버, 분 단위 컬럼(`RMV_USE_MIN`), 분기 경계일, 소프트 삭제 중복, 결측일
* 1회차: 정상 8/8 통과, **엣지 4/6 실패**(미등록 코드 `KeyError`, 분을 시간으로 읽어 사용시간 32,672h — 기대 545h의 60배) → Self-Correction → 2회차 **14/14 통과**(행 수 대조 21건 = legacy_agent 집계 21건) → `part_history_agent 0.1.0` 등록, 소요 3분 49초
* 답변: "Focus Ring 사용시간별 1차 Fail율 0~300h 11% / 300~600h 22% / 600h~ 25% → 600h 초과 시 위험 2.3배". 이후 운영자 승인으로 `1.0.0` 승격

### 오류 자가 복구 — Heal (SC-003, SC-005)

* 장비 SW v5.2 업데이트(장애 주입)로 FDC 로그 헤더·시간 형식이 바뀌어 `log_agent 1.1.0`이 `KeyError: RF_FWD_PWR` → 해당 항목만 "확인 불가"로 먼저 응답, 나머지 업무는 계속
* Jev 오류 분류 확신도 0.64 < 0.70 → 진단 코드 먼저 실행 후 재분류(포맷 변경 0.90)
* **로그 슬라이싱 진단**: 3 Run 약 17,103행 중 헤더 2종 + 오류 지점 전후 10행 + Run별 샘플 5행 = **37행(0.22%)만 관찰**해 원인 특정
* 패치 1회차(타임존 미지정 로그를 UTC로 가정) 회귀 42/44 실패 → AST 해시 블랙리스트 등록 → 2회차 44/44 통과 → `log_agent 1.1.1`, 같은 오류 시그니처의 `chamber_trend_agent 1.0.0 → 1.0.1` 연쇄 복구 → "확인 불가" 항목 재응답
* SC-005: 레거시 테이블 이관으로 데이터가 비어 복구 불가한 건은 예산 안에서 조기 중단 → 운영자 에스컬레이션(추측 답변 없음)

### 이력 기반 판단 진화 — Evolve (SC-006, SC-007)

* **SC-006 이력 리플레이**: 3년치 Qual 이력 3,000건을 그 시점의 가상 요청으로 재구성해 시간순 재생, 10개 분기 Walk-forward 진화, 최근 6개월(494건) Held-out. Time-Travel Guard가 `event_ts ≤ replay_clock`만 통과(필터·차단 17,863건, 누출 0건). 리플레이 중 구 SW 로그 Heal과 챔버추이 Agent Grow도 자연 발생 → Held-out 판정 일치율 **65.6% → 85.0%**
* **SC-007 운영 결과 학습**: ETX-300 Wet Clean에서 엔지니어 Override가 반복되자 L3가 편향 그룹을 감지하고, Override를 실제 결과로 검증(결과로 뒷받침된 Override만 반영, 근거 없는 보수적 Override는 학습 제외)한 뒤 판단 로직 후보 3개를 백테스트 → Focus Ring 사용시간 구간 보정안 채택(`spec_agent 1.3.0 → 1.4.0`, `part_history_agent` 의존 추가). Override율 **25% → 5%**, 1차 Pass율 백테스트 **71.5% → 86.6%**

### 구조·편성 진화와 자동 롤백 (SC-004, SC-005, SC-008)

* **SC-004 구조 진화**: Agent마다 복제된 FDC 파싱 코드(중복률 39%)와 반복 트레이스 로딩을 감지 → 공용 스킬 `fdc_toolkit` 추출 + 로딩 캐시 → 중복 **0%**, `log_agent` p50 **8.7s → 4.0s** (Shadow 24h 통과 후 승격). 병합안은 이때 기각되어 아카이브에 보관
* **SC-005 자동 롤백**: 승격 후 7일 Shadow 병행 중 PVD 장비군에서 판정 불일치 > 5% 감지 → Lineage 기준으로 결함 스킬에 의존하는 `log_agent`·`chamber_trend_agent`를 **원자적으로 동시 롤백**, 결함 버전 번호는 재사용하지 않고 수정본 재승격
* **SC-008 편성 전략 진화**: 편성 이력에서 결과 기여도 0인 호출 제거, 자주 쓰는 편성·계획 코드를 템플릿으로 승격(`super_agent 1.1.0 → 1.2.0`) → 요청당 호출 Agent **2.9 → 2.3**, 320건 중 64건을 LLM 계획 없이 처리해 응답 p50 **13.1s → 6.2s**

### 불필요 Agent 정리 — Retire (SC-009)

* SC-004에서 기각된 병합안이 아카이브에서 재출발해 `log_agent 2.0.0`(챔버 추이 기능 흡수)으로 채택
* `chamber_trend_agent`(기능 대체, 회귀 36건 + 최근 실제 요청 18건 재실행 54/54 일치)와 `lot_trace_agent`(75일 미사용)는 `deprecated` 유예 → 운영자 승인 → `retired`
* `part_history_agent`는 직접 호출은 0건이지만 `spec_agent 1.4.0`이 내부 호출하는 **간접 의존**을 찾아 폐기 보류(사유 기록)
* 이후 Lot 추적 재요청 시 새로 만들지 않고 아카이브에서 `lot_trace_agent 0.2.0`으로 복원

## Agent 구현 내용

### Super Agent (`super_agent`)

* 역할: 요청 해석·편성·CodeAct 실행 계획 작성·결과 종합·승인 게이트 연계
* 구현: LangGraph L1 Task Loop(`autoqual/loops/l1.py`) — `parse_request` → `retrieve_memory` → `jev_route` → `plan_codeact` → `execute_sandbox` → `observe` → `synthesize` → `respond` → `await_qual_result`(interrupt) → `deterministic_judge` → `approval_gate`(interrupt) → `apply_state_change` → `log_experience`. 분기 3개: 처리 불가 → Grow, 검증 실패 → 확인 불가 + Heal, 외부 장애 → 재계획 1회
* 응답 형식: `[Agent 편성] / [Qual 절차] / [챔버 상태] / [과거 이력] / [추천] / [판정]` 블록, 결론 먼저·근거는 수치·Spec·이력 건수
* 제약: 사람 승인 없는 상태 변경 금지, LLM 판정 금지, 근거 없는 결과를 정상으로 제시 금지

### 기준정보 Agent (`spec_agent`)

* 장비 모델·PM 종류별 Qual 절차(예: QP-ETX-WC-03), 측정 항목별 Spec, 기본 Seasoning 레시피·매수를 조회하고 교훈 보정(RF Reflected 증가율, 부품 사용시간 구간)을 적용해 추천 매수 산출
* 보정 시 교훈 ID·보정량을 명시, 기준정보 누락 시 기본값을 추정하지 않고 "기준정보 누락" 반환
* 버전: 1.0.0(초기) → 1.3.0(리플레이 진화) → 1.4.0(SC-007 판단 진화)

### 로그분석 Agent (`log_agent`)

* PM 전후 FDC 센서(RF Forward/Reflected, Pressure, Temp 등)·Leak·Base Pressure·알람을 SW 버전별 파서로 읽어 PM 전 대비 변화와 Seasoning에 영향을 주는 신호 탐지
* `read_fdc_trace(slice=header|around|sample)`로 원본 해상도 로그의 필요 구간만 조회, 파싱 실패는 빈 값·정상값으로 대체하지 않고 "확인 불가"
* 가장 많이 변한 Agent: Heal PATCH(1.1.1) → 공용 스킬 적용 MINOR → 롤백 → 수정본 → 챔버 추이 흡수 MAJOR(2.0.0)

### 레거시DB Agent (`legacy_agent`)

* 약어 컬럼·미문서화 코드값·폐기 테이블이 있는 레거시 DB를 스키마 탐색·코드값 해석 스킬(`legacy_sql_toolkit`, `code_value_resolver`)로 조회해 동일 챔버·PM 후 과거 Qual 이력, Seasoning 매수별 1차 Pass율, 재시도·Fail 패턴, 엔지니어 조치 제공
* 표본 수·기간을 반드시 함께 제시("최근 8회: 25매 1차 Pass율 50%"), 조회 0건을 "이력 없음"과 "데이터 부재(이관·미적재)"로 구분
* 리플레이 시 과거 건을 시간순 가상 요청으로 재구성하는 재료 제공

### 생성 Agent (Grow 산출물)

| Agent | 생성 시점 | 기능 | 최종 상태 |
| --- | --- | --- | --- |
| `chamber_trend_agent` | 리플레이 2024 Q3 구간 | Wet Clean 이후 RF 누적시간별 ER drift 추이 | `log_agent 2.0.0`에 흡수 → `retired` |
| `part_history_agent` | SC-002 운영 중 | 교체 부품 사용시간 ↔ 1차 Fail 분석 | `active`, `spec_agent` 간접 의존으로 폐기 보류 |
| `lot_trace_agent` | 일회성 요청 | 부품 Lot 장착 챔버 추적 | 미사용 → `retired` → 재요청 시 아카이브 복원 |

### Self-Evolving 엔진

* **Agent Factory (L2 Grow, `loops/l2_grow.py`)** — `search_archive`(기각·폐기 Genome 복원 우선) → `write_spec` → `explore_schema` → `generate_code_and_tests` → `run_tests`(정상 + 엣지 + 하네스 불변식, 기대값은 루프 밖 하네스가 원본 DB로 계산) → `register_probation`
* **Healer (L2 Heal, `loops/l2_heal.py`)** — `jev_classify_error` → `diagnose_codeact` → `write_patch` → `check_blacklist`(정규화 AST 해시) → `run_regression`(1건이라도 실패하면 반영 안 함) → `register_version` → `cascade` → `reanswer_pending`
* **Evolver / OpsEvolver (L3, `loops/l3_evolve.py`·`l3_ops.py`)** — `collect_metrics` → `jev_need_evolve` → `mutate`(최대 3후보, 아카이브에서 출발) → `evaluate_harness` → `select`(사람 승인) → `archive` → `shadow_run` → `promote` / `auto_rollback`, Retire 분기
* **ReplayEngine (`loops/replay.py`)** — `build_replay_requests` → `set_replay_clock` → L1 실행 → 실제 결과 비교 → 분기 종료 시 L3
* **버전 규칙** — `0.x` probation → `1.0.0` 첫 승격, Heal = PATCH, Evolve = MINOR, 구성 변경 = MAJOR, 결함 버전 번호 재사용 금지. 모든 변경은 Genome Lineage로 추적

### 도구 (CodeAct 안에서 `tools.xxx()`로 호출)

* 데이터 도구 12종: `lookup_equipment`, `query_spec_db`, `get_pm_event`, `read_fdc_trace`, `read_fdc_summary`, `read_alarm_log`, `inspect_legacy_schema`, `query_legacy_db`, `resolve_code_value`, `search_experience`, `unit_factor`, `call_agent`
* 시스템 도구: `execute_code`(샌드박스), `jev_decide`, `judge_qual`, `request_state_change`, `run_tests`, `evaluate_candidate`, `registry_*`, `archive_candidate`, `promote_or_rollback`, `analyze_dependency`, `patch_blacklist`, `set_replay_clock`, `inject_fault`
* 권한 프록시가 Genome에 선언된 도구만 통과시키고 모든 호출을 감사 로그에 남긴다

## 사용 기술/라이브러리

* Python 3.11 — Agent 본체·샌드박스·목업 Fab (`autoqual/` 약 8,300줄, `mock_env/` 약 1,700줄, `eval/` 약 900줄)
* LangGraph — L1/L2/L3 루프를 StateGraph·서브그래프로 구성, `InMemorySaver` 체크포인트, `interrupt`/`Command(resume)`로 측정값·승인 대기
* Python `ast` — CodeAct 정적 검사, 정규화 AST 해시(`canonical_hash`) 블랙리스트
* Pydantic — Agent 간 결과·요청 스키마 검증(`autoqual/schemas.py`), 검증 실패는 Heal 트리거
* Jev — 반복 분기 판단의 보정 확률 게이트(로컬 로지스틱 헤드 + 온도 스케일링, `config/jev.json` mode=http면 사내 엔드포인트)
* SQLite(WAL) / PostgreSQL — Registry·경험 메모리·아카이브·Lineage·감사 로그 단일 저장소
* FastAPI + SSE — 운영 API·실시간 이벤트 스트림(`ui/server.py`)
* React 19 + Vite + Tailwind v4 + shadcn/ui + React Flow + Zustand — 운영 콘솔(`ui/web`, TypeScript 약 6,100줄)
* unittest — 단위·API 테스트 31건 통과(`python -m unittest discover tests`), 레드팀·품질·성능 실측(`python -m eval.qa_suite --story`)
