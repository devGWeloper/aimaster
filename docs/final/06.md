# 회고 및 향후 계획

## 프로젝트 회고

### 잘된 점

* **"Agent가 스스로 바뀐다"를 수치와 이력으로 증명** — Grow·Heal·Evolve·Retire가 모두 실제 코드 변경(Genome 버전·diff·테스트)으로 남고, 9개 시나리오가 하나의 버전 원장으로 이어진다. "진화했다"는 주장을 Lineage와 Held-out 점수로 추적할 수 있다

* **자율성과 통제의 경계를 먼저 그은 설계** — 코드 작성·계획은 LLM, 반복 분기는 Jev, 판정·권한은 결정적 코드, 상태 변경은 사람으로 역할을 나누고, 평가 하네스·예산·Held-out을 루프 밖에 고정했다. 그 결과 Agent가 자기 코드를 바꾸는 시스템인데도 무승인 상태 변경·진화 퇴화·루프 폭주·미래 정보 누출이 모두 0건이었다

* **현실적인 목업** — 약어 컬럼, 미문서화 코드값, 폐기 테이블, SW 버전별 로그 포맷, 단위 혼재, 장비 모델·PM별 숨은 편향을 일부러 심었기 때문에 Heal·Grow·Evolve가 "연출"이 아니라 실제로 일어날 수밖에 없는 환경이 됐다

* **공격하는 관점의 테스트** — 개발 단계 검증과 별도로 레드팀·장애 주입·엣지 케이스를 수행해 의도 오분류, 미등록 장비, 에러 없는 오판, 시연 상태 꼬임 같은 결함을 찾아 고쳤고, 모두 단위 테스트로 고정했다

### 어려웠던 점과 배운 점

* **가장 위험한 실패는 에러가 나지 않는 실패** — 생성 코드의 60배 단위 오류, 단위 변경 34건의 1/1,000 값은 모두 예외 없이 그럴듯했다. 예외 처리가 아니라 값 자체를 검증하는 사후 검증과, 생성자와 분리된 오라클이 필요하다는 것을 배웠다

* **자기 수정 시스템에서 평가자는 성역이어야 한다** — 루프가 채점기를 import할 수 있으면 점수만 오르는 방향으로 진화한다. 하네스를 샌드박스 밖에 두고 단위 테스트로 그 경계를 고정한 것이 전체 신뢰성의 기반이었다

* **Loop Engineering은 "언제 멈출지"의 설계** — 진화를 잘 돌리는 것보다 예산·블랙리스트·조기 중단·에스컬레이션으로 "더 시도하지 않을 때"를 정하는 것이 중요했다. 복구 불가 2건을 억지로 고치지 않고 사람에게 넘긴 것도 설계대로의 결과다

* **보여주는 것도 기능** — 사용자 테스트에서 "무엇을 하는 Agent인지 모르겠다", "너무 빨리 지나간다"는 피드백을 받았다. 업무 흐름 바, Agent가 대신 답하는 업무 질문, 변경 스포트라이트, 설명용 재생 속도를 넣고 나서야 자율 에이전트의 동작이 현업에게 전달됐다

## 기술적 한계

* **사내 LLM API 실연동 미검증** — 현재 수치는 오프라인 Playbook(기능 플래그 → 결정적 코드) 기준이라 실제 LLM의 코드 생성 품질·지연·비용이 반영되지 않았다
* **Jev 대체 구현** — 사내망 반입 전 로컬 보정 로지스틱 헤드로 대체되어 있어 판단 품질 평가가 목업 분포에 묶여 있다
* **단일 프로세스 저장소** — SQLite(WAL) 단일 프로세스라 다중 운영자·동시 요청·대규모 리플레이(3,000건에 수 분) 부하 테스트를 하지 못했다
* **목업 데이터의 한계** — 실데이터를 쓸 수 없어 업무 경험 기반으로 현실감을 설계했지만, 실제 장비 SW 변경·레거시 스키마 이관 이력과는 분포가 다를 수 있다
* **작은 표본** — Agent 생성 성공률(3건)·자가 복구율(7건)은 분모가 작아 통계적 신뢰 구간이 넓다
* **운영 UI 범위** — 1,440px 이상 데스크톱 기준이며 모바일·다국어·접근성은 검증하지 않았다. 인증은 로컬 단일 운영자 콘솔 수준이다
