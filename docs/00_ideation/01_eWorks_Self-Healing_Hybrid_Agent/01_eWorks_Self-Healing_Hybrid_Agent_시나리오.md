### 핵심 사용자 시나리오

**시나리오 1 : 하이브리드 라우팅 기반 액션 요청 처리**

* ID : SC-001

* 상황 : 현업 담당자가 eWorks Agent에 일상적인 조회·처리 요청을 입력할 때

* 목표 : 단순 요청은 즉시, 복잡한 요청은 정확하게 처리받는 것

* 사전 조건 : eWorks Agent에 Jev(System 1) 판단 스키마와 LLM(System 2) 연동 완료, 확신도 임계값 설정 완료, 업무 툴(API) 등록 완료

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 요청 입력 | 요청 + 현재 상태를 Jev에 전달, 의도·대상 툴·파라미터를 타입 판단으로 반환 | 70~500ms 수준 |
| 2 | - | 확신도 ≥ 임계값이면 즉시 툴 실행, 미만이면 LLM으로 에스컬레이션 | 라우팅 결과 로그 기록 |
| 3 | - | LLM이 복잡한 요청을 분해·추론 후 툴 실행 계획 수립 및 실행 | 에스컬레이션 건만 |
| 4 | 결과 확인 | 처리 결과와 처리 경로(Jev/LLM), 확신도 표시 | 디버깅·KPI 측정용 |

* 입력 예시

```
[요청 A] 내 결재 대기 건 보여줘
[요청 B] 지난달 반려된 건들 중에 같은 사유로 반려된 게 있는지 분석해서 정리해줘
```

* 기대 출력

```
[요청 A]
- 경로: Jev (확신도 0.97) → 툴: approval.list_pending
- 응답시간: 0.3s
- 결과: 결재 대기 3건 (목록 표시)

[요청 B]
- 경로: Jev (확신도 0.41) → LLM 에스컬레이션
- 사유: 다단계 분석·요약 필요
- 응답시간: 8.2s
- 결과: 반려 12건 중 "증빙 누락" 사유 5건 반복, 상세 목록 및 개선 제안
```

* 성공 기준

  * 기준 1: 단순 요청의 70% 이상이 Jev 경로로 처리되고 평균 응답시간 1초 이내

  * 기준 2: Jev 경로 처리 건의 정답률이 LLM 단독 처리 대비 동등 수준(차이 3%p 이내) 유지

**시나리오 2 : 실패 요청의 자가 수정 및 검증 반영**

* ID : SC-002

* 상황 : 에이전트가 특정 유형의 요청 처리에 반복 실패했을 때

* 목표 : 개발자 개입 없이 에이전트가 원인을 찾아 스스로 수정하고, 검증된 수정만 반영되는 것

* 사전 조건 : 실행 로그 수집 체계 구축, evolve셋·held-out셋 분리된 테스트셋 준비, 샌드박스 실행 환경 구성

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | (요청 실패 발생) | 실패 실행 기록 수집, 실패 유형 분류(툴 파라미터 오류/의도 오분류/프롬프트 결함 등) | 자동 트리거 |
| 2 | - | 하네스 코드(프롬프트·툴 코드·제어 흐름) 읽고 수정안 생성 | 1회 수정 범위 제한(RRSI) |
| 3 | - | 샌드박스에서 evolve셋으로 검증, 과적합 탐지(leakage critic) 후 held-out셋 검증 | 노이즈 범위 내 개선은 기각 |
| 4 | 운영자 변경 내역 검토·승인 | 통과한 수정만 반영, 변경 이력·전후 성능 리포트 생성 | 롤백 가능 |
| 5 | - | 같은 유형 요청 재실행으로 개선 확인 | 회귀 테스트 자동 수행 |

* 입력 예시

```
[실패 로그]
- 요청: "11월 출장비 정산 건 상태 알려줘"
- 처리 경로: Jev → expense.get_status(month="11월")
- 오류: InvalidParameter - month must be YYYY-MM format
- 동일 유형 실패: 최근 7일 14건
```

* 기대 출력

```
[자가 수정 리포트]
- 원인: 날짜 파라미터 정규화 로직 부재
- 수정 대상: tools/expense.py (날짜 정규화 함수 추가), 툴 스키마 설명 보완
- evolve셋: 실패 14건 중 14건 해결
- held-out셋: 성공률 86.2% → 89.5% (+3.3%p), 기존 통과 건 회귀 0건
- 판정: 반영 승인 대기
```

* 성공 기준

  * 기준 1: 실패 케이스의 60% 이상을 사람 개입 없이 수정안 생성 및 검증 통과

  * 기준 2: 반영된 수정이 held-out셋 성능을 저하시키지 않음(회귀 0건)
