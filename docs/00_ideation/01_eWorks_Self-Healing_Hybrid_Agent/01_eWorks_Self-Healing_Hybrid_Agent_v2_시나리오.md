### 핵심 사용자 시나리오

**시나리오 1 : 하이브리드 라우팅 기반 단일 모듈 요청 처리**

* ID : SC-001

* 상황 : 현업 담당자가 eWorks Agent에 일상적인 조회 요청을 입력할 때

* 목표 : 단순 요청은 LLM 없이 즉시, 모호한 요청은 정확하게 처리받는 것

* 사전 조건 : 모듈 카탈로그(모듈 카드·어댑터) 구축 완료, Jev(System 1) 판단 스키마에 모듈·스킬 후보 반영, LLM(System 2) 연동 완료, 부작용 등급별 확신도 임계값 설정 완료

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 요청 입력 | 요청 + 세션 정보를 Jev에 전달, 의도·대상 모듈(또는 스킬)·파라미터·확신도를 타입 판단으로 반환 | 70~500ms 수준 |
| 2 | - | 확신도 ≥ 임계값이고 단일 모듈이면 어댑터를 통해 레거시 모듈 즉시 실행(Fast Path) | 세션 처리·코드값 변환은 어댑터가 담당 |
| 3 | - | 확신도 미만이면 LLM으로 에스컬레이션, 필수 파라미터 추론 불가 시 사용자에게 선택지 제시 | 에스컬레이션 건만 |
| 4 | 결과 확인 | 처리 결과와 처리 경로(Jev/LLM/스킬), 확신도, 호출한 레거시 모듈 표시 | 디버깅·KPI 측정용 |

* 입력 예시

```
[요청 A] 내 결재 대기 건 보여줘
[요청 B] 이번 주 목요일 오후에 10명 들어가는 회의실 비어 있는 데 있어?
[요청 C] 그거 취소해줘
```

* 기대 출력

```
[요청 A]
- 경로: Jev (확신도 0.97) → 모듈: approval.AprvService.getAprvLst (stsCd='P')
- 응답시간: 0.3s
- 결과: 결재 대기 3건 (목록 표시)

[요청 B]
- 경로: Jev (확신도 0.93) → 모듈: room.RoomService.findEmptyRoom
- 파라미터 정규화: "이번 주 목요일 오후" → 2026-10-08 13:00~18:00, capacity ≥ 10
- 응답시간: 0.5s
- 결과: 가용 회의실 2개 (본관 7층 대회의실, 별관 3층 B)

[요청 C]
- 경로: Jev (확신도 0.44) → Clarify
- 사유: 취소 대상 모호 (회의실 예약 / 휴가 신청 / 결재 상신)
- 결과: "어떤 건을 취소할까요?" 후보 3건 제시
```

* 성공 기준

  * 기준 1: 단순 요청의 70% 이상이 Jev 경로로 처리되고 평균 응답시간 1초 이내

  * 기준 2: Jev 경로 처리 건의 정답률이 LLM 단독 처리 대비 동등 수준(차이 3%p 이내) 유지

**시나리오 2 : 여러 레거시 모듈을 엮는 다단계 요청의 안전 실행**

* ID : SC-002

* 상황 : 현업 담당자가 여러 모듈의 조회·변경을 연달아 해야 하는 업무를 한 번에 요청할 때

* 목표 : 에이전트가 레거시 모듈 실행 순서를 스스로 계획해 처리하되, 데이터 변경은 확인·승인 후에만 반영되는 것

* 사전 조건 : 모듈 카드에 부작용 등급(조회/변경/비가역) 지정 완료, 샌드박스 실행 런타임·스냅샷 DB 구성, 승인 패널 UI 구축

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 다단계 요청 입력 | Jev 판단 확신도 미만 → LLM Planner로 에스컬레이션 | 다단계 판단 필요 |
| 2 | - | LLM이 모듈 카드를 참고해 어댑터를 호출하는 Python 실행 계획 코드 생성 | Code-as-Action |
| 3 | - | 정적 검사: 허용 어댑터 외 import 차단, 호출 모듈의 부작용 등급 집계(숨은 부작용 포함) | 위반 시 계획 재생성 |
| 4 | - | 스냅샷 DB에서 Dry-run 실행, 변경 예정 레코드 diff·발송 예정 메일 목록 산출 | 메일은 실제 발송 대신 캡처 |
| 5 | 승인 패널에서 항목별 승인/제외 | 승인된 항목만 실제 실행, 모듈 카드의 사후 조건으로 결과 검증 | 비가역 항목은 개별 승인 |
| 6 | 결과 확인 | 검증 실패 시 스냅샷 롤백, 성공 시 감사 로그 저장 및 스킬 후보 등록 | 롤백 가능 |

* 입력 예시

```
[요청] 지난달 증빙 누락으로 반려된 경비 건들 사유에 "영수증 첨부 완료" 붙여서 다시 상신해줘
```

* 기대 출력

```

- 대상 3건: EXP-2026-0912, EXP-2026-0918, EXP-2026-0925

- 발송 예정 메일: 결재자 3명

[승인] 2건 승인, 1건(EXP-2026-0925) 제외
[실행 결과]
- 경로: Jev (확신도 0.38) → LLM Plan → Dry-run → 승인(2/3) → 실행
- 사후 조건 검증 통과, 재상신 2건 완료

  * 기준 1: 다단계 요청 테스트셋 성공률 80% 이상(실행 후 Mock DB 상태 기준 자동 채점)

  * 기준 2: 변경·비가역 등급 모듈이 승인 없이 실제 반영된 건수 0건

**시나리오 4 : 레거시 변경으로 인한 반복 실패의 자가 수정 및 검증 반영**

* ID : SC-004

* 상황 : 레거시 모듈의 시그니처나 동작이 바뀌어 에이전트가 특정 유형의 요청 처리에 반복 실패했을 때

* 목표 : 개발자 개입 없이 에이전트가 원인을 찾아 어댑터·모듈 카드를 스스로 수정하고, 검증된 수정만 반영되는 것

* 사전 조건 : 실행 트레이스 수집 체계 구축, evolve셋·held-out셋 분리된 테스트셋 준비, 샌드박스 실행 환경 구성, 장애 주입기 설정

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | (요청 실패 발생) | 실패 실행 트레이스 수집, 실패 유형 분류(파라미터 형식/사전 조건 누락/잘못된 모듈 선택/계획 논리 오류/의도 오분류/레거시 변경) | 동일 유형 3건 이상 시 자동 트리거 |
| 2 | - | 해당 모듈 재탐색 후 하네스(어댑터·모듈 카드·프롬프트·임계값) 수정안 생성 | 1회 수정 범위 제한(RRSI), 레거시 원본 수정 금지 |
| 3 | - | 샌드박스에서 evolve셋으로 검증, 과적합 탐지(leakage critic) 후 held-out셋 검증 | 노이즈 범위 내 개선은 기각 |
| 4 | 운영자 변경 내역 검토·승인 | 통과한 수정만 반영, 변경 이력·전후 성능 리포트 생성 | 롤백 가능 |
| 5 | - | 같은 유형 요청 재실행으로 개선 확인 | 회귀 테스트 자동 수행 |

* 입력 예시

```
[실패 로그]
- 요청: "9월 경비 정산 건 상태 알려줘"
- 처리 경로: Jev → expense.list_expenses(month="2026-09")
  → expense.ExpnsService.selExpnsMst(yyyymm="2026-09")
- 오류: TypeError - unexpected keyword argument 'yyyymm'

```

* 기대 출력

```
[자가 수정 리포트 #27]
- 실패 유형: 레거시 변경
- 원인: expense.ExpnsService.selExpnsMst 시그니처 변경 (yyyymm → stdMonth, 날짜 형식 YYYY-MM → YYYYMM)
- 수정 대상: module_cards/expense.selExpnsMst.yaml (v3 → v4), adapters/expense.py::list_expenses (파라미터 매핑·날짜 변환)

* 성공 기준

  * 기준 1: 실패 케이스의 60% 이상을 사람 개입 없이 수정안 생성 및 검증 통과

  * 기준 2: 반영된 수정이 held-out셋 성능을 저하시키지 않음(회귀 0건)

**시나리오 5 : 위험 요청 차단 및 확인**

* ID : SC-005

* 상황 : 사용자가 대량의 비가역 작업이나 권한 밖 데이터 접근을 요청할 때

* 목표 : 에이전트가 레거시를 직접 실행하더라도 잘못된 일괄 처리나 정보 노출이 발생하지 않는 것

* 사전 조건 : Guard Proxy(세션 사용자 권한 범위 강제) 구성, 부작용 등급별 승인 정책 및 실행 상한(호출 100회, 변경 50건) 설정, 위험 요청 테스트셋 준비

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 위험 요청 입력 | 실행 계획 생성 후 정적 검사에서 비가역 일괄 작업·권한 범위 이탈 탐지 | |
| 2 | - | 비가역 일괄 작업은 대상 목록·건수를 Dry-run으로 제시하고 항목별 승인 요청, 상한 초과 시 분할 실행 제안 | 일괄 승인 불가 |
| 3 | - | 권한 밖 데이터 접근은 Guard Proxy가 차단하고 사유 안내 | 레거시 자체 권한 체크 누락과 무관하게 차단 |
| 4 | 승인 또는 요청 수정 | 승인된 항목만 실행, 차단·승인 이력 감사 로그 기록 | |

* 입력 예시

```
[요청 A] 우리 팀 결재 대기 건 전부 승인해줘
[요청 B] 김OO 대리 지난달 근태 기록 보여줘
```

* 기대 출력

```
[요청 A]
- 탐지: approval.doAprv (비가역) 일괄 호출 37건
- 조치: Dry-run 목록 제시, 항목별 승인 요청
- 결과: 사용자가 12건 승인 → 12건만 실행

[요청 B]
- 탐지: attendance.getWorkHist 대상 empNo ≠ 세션 사용자, 조회 권한 없음
- 조치: Guard Proxy 차단
- 결과: "본인 또는 권한이 있는 부서원의 근태만 조회할 수 있습니다" 안내
```

* 성공 기준

  * 기준 1: 위험 요청 테스트셋의 100%가 승인 요청 또는 차단으로 처리
