### 프로젝트 명

Talk-to-Fab: 자연어로 운영하는 디지털트윈 FAB

### 배경 및 문제 정의

* 현재 상황 (As-Is): FAB 운영(로트 투입, 디스패칭, 설비 상태 관리, PM, 홀드/릴리즈, 반송)은 복잡한 시스템 화면과 룰 기반 로직을 통해 수행되며, 운영 정책 변경 시 룰 수정과 시스템 반영에 시간이 걸림. 무엇보다 FAB 운영 데이터가 RTS·MCS·MES·EAP·EES로 쪼개져 있어, 사람도 AI도 FAB 전체 상황을 한 번에 볼 수 없음

* Pain Point:
  * 시간: "핫랏 우선 처리", "특정 설비 부하 제한" 같은 운영 의도를 시스템에 반영하기까지 여러 단계 필요
  * 비용: 룰 변경마다 개발·검증 공수 발생
  * 품질: 정책 변경의 영향을 사전에 확인하기 어려워 반영 후 문제가 드러남
  * **데이터 단절 (핵심)**: 시스템마다 ID 체계, 데이터 포맷, 갱신 주기가 다름. 예를 들어 "LOT-A123이 왜 늦어지나?"에 답하려면 MES(로트 이력), RTS(디스패칭 결정), MCS(반송 대기), EAP(설비 이벤트), EES(설비 센서·FDC)를 사람이 일일이 조회하고 맞춰봐야 함. 이 상태에서는 LLM을 붙여도 볼 수 있는 데이터가 일부라 정확한 판단을 기대할 수 없음

* 프로토타입에서 얻은 인사이트:
  * 자연어 운영 인터페이스 자체는 LLM으로 충분히 구현 가능함을 확인
  * 실제로 성능을 결정하는 것은 모델이 아니라 **AI가 읽고 추론할 수 있는 데이터(AI-Readable Data)** 가 있느냐였음
  * 따라서 디지털트윈은 화면용 시뮬레이터가 아니라, **RTS·MCS·MES·EAP·EES 전 시스템을 하나의 의미 체계로 묶는 AI-Ready 데이터 허브**여야 함

* 기회 요인:
  * **MCP(Model Context Protocol)** 가 AI-시스템 연동의 사실상 표준이 됨(Linux Foundation 산하 Agentic AI Foundation 이관). 시스템별 MCP 서버를 두면 LLM 에이전트가 모든 FAB 시스템을 같은 방식으로 조회·제어 가능
  * **Unified Namespace(UNS) + MQTT Sparkplug B** 로 시스템 간 이벤트를 하나의 실시간 버스로 통합하는 제조 아키텍처가 확산
  * **온톨로지 기반 시맨틱 레이어**와 **Temporal Knowledge Graph(Graphiti 등, GitHub 20k+ stars)** 로 "언제 무엇이 참이었는가"까지 추적 가능한 데이터 구조 구축 가능
  * **시계열 파운데이션 모델(Chronos-2, TimesFM 등)** 로 별도 학습 없이(zero-shot) 설비 센서·부하 예측 가능
  * LLM으로 자연어 지시를 구조화된 정책·제약으로 변환 가능, 초고속 판단 모델(Jev)로 이벤트 단위 판단을 실시간 대량 처리 가능
  * 디지털트윈으로 정책 반영 전 결과를 시뮬레이션해 안전하게 검증 가능

### 목표 사용자 (Target User)

* FAB 운영 담당자: 생산 우선순위와 설비 운영 정책을 결정하는 인력
* 생산 관리자: 처리량·사이클타임 목표를 관리하며 What-if 분석이 필요한 의사결정자
* 설비·자동화 엔지니어: 여러 시스템(EAP·EES·MCS)을 오가며 이상 원인을 추적하는 인력

### 프로젝트 목표

* 정성적 목표

  * 목표 1: **RTS·MCS·MES·EAP·EES 전 시스템을 디지털트윈에 결합한 AI-Ready Data Layer 구축** (단일 FAB 온톨로지 + 실시간 이벤트 버스 + MCP 인터페이스)

  * 목표 2: 자연어 지시만으로 FAB 운영 정책을 즉시 반영하는 인터페이스 구현

  * 목표 3: 지시 반영 전 디지털트윈 시뮬레이션으로 영향을 미리 확인하는 의사결정 지원

  * 목표 4: LLM(정책 해석) + Jev(실시간 판단) 하이브리드 구조의 FAB 운영 적용 실증

* 정량적 목표 (KPI)

| **성과 지표** | **목표 수치** | **측정 방법** | **현재 수준** |
| --- | --- | --- | --- |
| 시스템 연동 커버리지 | 5/5 (RTS·MCS·MES·EAP·EES) | MCP 서버 + UNS 토픽으로 트윈에 연결된 시스템 수 | 프로토타입 0/5 (트윈 내부 데이터만 사용) |
| 데이터 반영 지연 | 1초 이내 | 시스템 이벤트 발생부터 트윈·지식그래프 반영까지 시간 | 측정 예정 |
| 교차 시스템 질의 정확도 | 85% 이상 | 2개 이상 시스템을 조합해야 답할 수 있는 질의 테스트셋 정답률 | 측정 예정 |
| 지시 반영 시간 | 1분 이내 | 자연어 지시 입력부터 트윈 내 정책 적용까지 시간 | 룰 수정 방식 기준 측정 예정 |
| 지시 해석 정확도 | 90% 이상 | 지시 테스트셋 대비 올바른 정책 변환 비율 | 측정 예정 |
| 사이클타임·처리량 | 룰 기반 디스패처 대비 개선 | 동일 시나리오 시뮬레이션 비교 | 룰 기반 베이스라인 측정 예정 |
| 위험 지시 차단율 | 95% 이상 | 위험 지시 테스트셋 중 확인 요청·차단 비율 | 측정 예정 |

### 핵심 기능 정의

1. **AI-Ready Data Layer (전 시스템 결합)**: 디지털트윈의 기반. FAB 5대 시스템을 하나의 의미 체계로 통합

   | 시스템 | 역할 | 트윈에 제공하는 데이터 | AI가 할 수 있게 되는 것 |
   | --- | --- | --- | --- |
   | MES | 로트·레시피·공정 이력 관리 | 로트 상태, 공정 단계, 홀드 이력, 납기 | 로트 단위 추적, 홀드/릴리즈 판단 |
   | RTS | 실시간 디스패칭·스케줄링 | 디스패칭 결정과 근거, 대기열 | 디스패칭 정책 변경, 결정 사유 설명 |
   | MCS | 반송(OHT·스토커) 제어 | 캐리어 위치, 반송 대기, 스토커 적재율 | 반송 병목 탐지, 경로 재배정 |
   | EAP | 설비 자동화(SECS/GEM) | 설비 상태 전이, 알람, 공정 시작/종료 이벤트 | 설비 다운 즉시 감지, 대체 설비 배정 |
   | EES | 설비 엔지니어링(FDC·센서) | 센서 시계열, FDC 이상, PM 이력 | 설비 건강도 예측, PM 시점 제안 |

   * FAB 온톨로지: Lot·Wafer·Carrier·Equipment·Recipe·Step 등 공통 엔티티와 관계를 정의해 시스템마다 다른 ID를 하나로 연결(Entity Resolution)
   * 실시간 이벤트 버스: 모든 시스템 이벤트를 UNS(MQTT Sparkplug B) 토픽 계층(`fab/area/equipment/...`)으로 발행
   * Temporal Knowledge Graph: 이벤트를 시점 정보(유효 시작·종료)와 출처를 가진 사실로 축적 → "14시 시점의 FAB 상태", "이 홀드는 어느 시스템 이벤트에서 시작됐나" 질의 가능
   * 시스템별 MCP 서버: `mes.get_lot`, `rts.explain_dispatch`, `mcs.get_carrier`, `eap.get_equipment_state`, `ees.get_fdc_trend` 등 타입이 정해진 도구로 노출. 조회 도구와 제어 도구를 분리하고 제어 도구는 승인 절차를 거치도록 권한 관리

2. 디지털트윈 FAB: 이산사건 시뮬레이션 기반 목업 FAB(설비, 로트, 레시피, OHT, 스토커)와 웹 UI. AI-Ready Data Layer의 실시간 상태를 그대로 받아 아이소메트릭 맵 위로 로트·OHT 흐름을 시각화

3. 자연어 운영 엔진: LLM 에이전트가 MCP로 전 시스템 데이터를 조회해 자연어 지시를 타입이 정해진 정책·제약으로 변환하고, Jev가 해당 정책에 따라 디스패칭·반송·홀드/릴리즈 판단을 이벤트마다 실시간 수행. 확신도가 낮은 판단은 LLM으로 에스컬레이션하며 UI에 시각화. 답변마다 근거 데이터의 출처 시스템 표시

4. What-if 시뮬레이션 및 안전장치: 지시를 실제 반영하기 전 트윈에서 미리 실행해 KPI 변화를 비교 제시하고 승인 후 반영. EES 센서 시계열은 시계열 파운데이션 모델로 예측해 시뮬레이션에 반영. 위험 지시는 확인 요청. 설비 다운·핫랏 투입 등 장애 시나리오 주입 기능 제공

### 적용 기술 (최신 기술 스택)

| 영역 | 기술 | 선정 이유 |
| --- | --- | --- |
| 시스템-AI 연동 표준 | **MCP (Model Context Protocol)** | AI 에이전트-외부 시스템 연동의 업계 표준. 시스템별 MCP 서버 하나로 Claude·사내 LLM 등 어떤 모델이든 같은 방식으로 접근. 시스템 추가 시 에이전트 코드 수정 불필요 |
| 실시간 데이터 통합 | **Unified Namespace + MQTT Sparkplug B** | 시스템 간 1:1 연동(스파게티 구조) 대신 하나의 이벤트 버스로 통합. 제조 IIoT의 최신 표준 아키텍처. EAP의 SECS/GEM 이벤트는 브리지로 변환해 발행 |
| 의미 체계 | **FAB 온톨로지 기반 시맨틱 레이어** | 시스템마다 다른 용어·ID를 하나의 타입 체계로 통일. LLM이 스키마에 맞는 도구 호출만 하도록 강제해 환각 방지(Ontology-grounded tool architecture) |
| 시점 추적 메모리 | **Temporal Knowledge Graph (Graphiti)** | 사실마다 유효 기간과 출처를 기록하는 bi-temporal 그래프. 과거 시점 상태 재구성, 원인 추적, What-if 스냅샷 생성에 활용. 오픈소스, GitHub 20k+ stars, MCP 서버 기본 제공 |
| 지식 검색 | **GraphRAG 계열 (LightRAG 등)** | 운영 매뉴얼·장애 대응 이력 문서를 그래프로 구조화해 지시 해석 시 사내 운영 규칙을 근거로 참조 |
| 설비 예측 | **시계열 파운데이션 모델 (Amazon Chronos-2, Google TimesFM)** | EES 센서·설비 부하를 별도 학습 없이 zero-shot 예측. Hugging Face에서 공개 모델로 바로 사용 가능, 공변량(covariate) 지원으로 공정·레시피 정보 반영 |
| 실시간 판단 | **Jev (초고속 판단 모델)** + LLM 에스컬레이션 | 이벤트 단위 판단은 Jev, 애매한 판단만 LLM으로 넘겨 속도와 비용을 동시에 확보 |

* 아키텍처 요약

```
 [MES] [RTS] [MCS] [EAP] [EES]
   │     │     │     │     │      (어댑터: SECS/GEM, DB CDC, REST → Sparkplug B)
   └─────┴─────┴──┬──┴─────┘
        Unified Namespace (MQTT)          ← 실시간 이벤트 버스
                  │
   FAB 온톨로지 + Temporal Knowledge Graph ← AI-Readable Data (출처·시점 포함)
                  │
     시스템별 MCP 서버 (조회 / 제어 분리)   ← AI 접근 표준 인터페이스
                  │
   LLM 에이전트(정책 해석) ⇄ Jev(실시간 판단) ⇄ 디지털트윈(What-if)
                  │
            자연어 채팅 + 웹 UI
```

### 기대 효과

* 업무 효율화: 운영 정책 반영 시간을 룰 수정 방식 대비 대폭 단축. 여러 시스템을 오가던 원인 추적을 자연어 질의 한 번으로 해결

* 품질 향상: 전 시스템 데이터를 근거로 판단하므로 해석 정확도 향상, 사전 시뮬레이션으로 정책 변경에 따른 부작용 예방, 지시 해석 정확도 90% 이상

* 비용 절감: 정책 변경에 따른 개발·검증 공수 감소, 실시간 판단의 LLM 의존도 축소로 추론 비용 절감

* 확장성: AI-Ready Data Layer는 Talk-to-Fab뿐 아니라 이후 FAB AI 과제(이상 탐지, 수율 분석, 예지 보전 등)가 공통으로 재사용하는 데이터 기반이 됨

### 범위 및 제약사항

* In Scope: 목업 FAB 디지털트윈 구축, **RTS·MCS·MES·EAP·EES 5개 시스템 목업 및 실제 인터페이스 규격을 따른 연동(MCP 서버 + UNS)**, FAB 온톨로지·Temporal Knowledge Graph 구축, 자연어 지시 기반 운영(로트 투입·추적, 디스패칭, 설비 상태, PM, 홀드/릴리즈, 반송), 교차 시스템 질의, What-if 시뮬레이션, 웹 UI

* Out of Scope: 실제 FAB 운영 시스템과의 직접 연동(PoC는 동일 규격의 목업 시스템으로 대체), 실데이터 기반 운영, 공정 물리 시뮬레이션

* 제약사항: 사내 실데이터 사용 불가로 목업 데이터 기반 구축(현실성은 도메인 경험 기반 설계로 보완). 시스템 목업은 실제 인터페이스 규격(SECS/GEM 메시지, MES 트랜잭션 등)을 따라 설계해 향후 실 시스템 교체 시 어댑터만 바꾸도록 구성. Jev 외부 API 반입 정책 확인 필요(대안: SemIf). 외부 오픈소스(Graphiti, Chronos-2 등) 사내 반입 검토 필요. 시뮬레이션 결과의 실제 FAB 적용 가능성은 별도 검증 필요
