### 시나리오 공통 전제 : 타임라인과 Agent 버전

시나리오 번호는 기능 단위 순서이며, 실제 발생 순서는 아래 타임라인을 따른다. **가장 먼저 일어나는 것은 운영 투입 전의 이력 리플레이(SC-006)** 이고, 이후 시나리오는 모두 리플레이로 사전 진화된 버전에서 출발한다. 모든 시나리오의 Agent 버전은 아래 원장과 일치한다.

**버전 규칙**

| 구분 | 규칙 | 예시 |
| --- | --- | --- |
| `0.x.y` | Grow로 생성된 직후 `probation` 상태 (정식 승격 전) | `part_history_agent 0.1.0` |
| `1.0.0` | 운영자 승인으로 첫 `active` 승격 | `part_history_agent 0.1.0 → 1.0.0` |
| PATCH (`x.y.Z`) | Heal 패치 (오류 복구) | `log_agent 1.4.0 → 1.4.1` |
| MINOR (`x.Y.0`) | Evolve 채택 (판단 로직·성능 개선, 공용 스킬 적용) | `spec_agent 1.3.0 → 1.4.0` |
| MAJOR (`X.0.0`) | Agent 구성 변경 (병합·기능 흡수·분리) | `log_agent 1.5.1 → 2.0.0` |
| 롤백 | 직전 안정 버전으로 복귀, 결함 버전 번호는 재사용하지 않고 수정본은 다음 번호 부여 | `log_agent 1.5.0 → 1.4.1`, 수정본 `1.5.1` |

| --- | --- | --- | --- | --- |

### 핵심 사용자 시나리오

**시나리오 1 : PM 후 AutoQual 요청에 대한 멀티 에이전트 자율 협업**

* ID : SC-001

* 시점·버전 : 2026-09-03 (운영 3일차) / `super_agent 1.1.0`, `spec_agent 1.3.0`, `log_agent 1.4.0`, `legacy_agent 1.2.0`

* 상황 : 설비 엔지니어가 장비 PM(정기 보수)을 마치고 장비를 다시 생산에 투입(Up)하려 할 때

* 목표 : 요청 한 줄로 Qual 절차 확인, Seasoning 계획 수립, Qual 결과 판정, Up 전환 승인 요청까지 받는 것

* 사전 조건 : 리플레이(SC-006)로 사전 진화된 버전 운영 투입 완료, CodeAct 샌드박스 런타임·권한 프록시 구성, Jev 판단 게이트 연동, 목업 기준정보 DB·장비 로그·레거시 이력 DB 구축

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 AutoQual 요청 입력 | Super Agent가 요청을 해석하고 Jev가 필요한 Agent를 확률과 함께 선택 | 확신도 높으면 LLM 편성 생략 |
| 2 | - | Super Agent가 하위 Agent 병렬 호출·결과 결합·판정 순서를 Python 실행 계획 코드로 작성 | CodeAct |
| 3 | - | 기준정보 Agent: 장비 모델·PM 종류별 Qual 절차, Spec, 기본 Seasoning 매수 조회 + 조건이 맞는 교훈 보정 적용 | |
| 4 | - | 로그분석 Agent: PM 후 Leak·Base Pressure 로그, 알람, PM 전 대비 FDC 센서 트레이스 이상 여부 분석 | |
| 5 | - | 레거시DB Agent: 동일 챔버·동일 PM 후 과거 Qual 이력에서 Seasoning 매수별 1차 Pass율 분석 | 약어 컬럼·코드값 해석 포함 |
| 6 | Qual 계획 확인 | Super Agent가 결과를 종합해 Seasoning 매수와 Qual 순서를 근거(지표·이력·교훈 ID)와 함께 제시 | |
| 7 | Qual 진행 후 판정 요청 | Particle·ER 모니터 결과를 수집해 판정 코드로 Spec 비교 | 판정은 결정적 코드 수행 |
| 8 | Up 전환 승인 | Pass 시 장비 상태 변경 요청을 승인 패널로 전달, 승인 후에만 반영 | L1 Task Loop 종료 |

* 입력 예시

```
[요청] ETCH-07 B챔버 Wet Clean PM 끝났어. AutoQual 진행해줘
```

* 기대 출력

```
[Agent 편성] super_agent 1.1.0
- 경로: Jev (spec_agent 0.98 / log_agent 0.95 / legacy_agent 0.91 / chamber_trend_agent 0.41 제외) → 3개 Agent 병렬 실행
- 편성 시간: 0.3s

[Qual 절차] (spec_agent 1.3.0)
- 모델 ETX-300 / PM: WET_CLEAN → 절차 QP-ETX-WC-03
- Leak Check → Seasoning → Particle(≤15ea) → ER Monitor(1,850±5% Å/min, Unif ≤3%)
- 기본 Seasoning: 25매

[챔버 상태] (log_agent 1.4.0)
- Leak Rate 0.8 mTorr/min (Spec ≤2.0) 정상, PM 후 알람 없음
- RF Reflected Power 초기값 PM 전 대비 +12%

[과거 이력] (legacy_agent 1.2.0)
- 동일 챔버 Wet Clean 후 최근 8회 (2025-03 ~ 2026-08): 25매 1차 Pass 2/4 (50%), 35매 1차 Pass 4/4 (100%)
- 25매 Fail 2건 모두 PM 후 RF Reflected +10% 이상

[추천] Seasoning 35매 → Particle → ER Monitor
- 보정: 기본 25매 + 10매 [교훈 L-0007: ETX-300 Wet Clean 후 RF Reflected +10% 이상 → +10매, 리플레이 학습·원천 이력 23건]

[판정 - Qual 완료 후] (judge_qual)
- Particle 9ea / ER 1,872 Å/min / Unif 2.1% → Qual PASS
- 승인 요청: ETCH-07 B챔버 DOWN → UP 전환
```

* 엣지 케이스

| 케이스 | 상황 | 시스템 동작 | 기대 결과 |
| --- | --- | --- | --- |
| 1차 Qual Fail 반복 | Particle 18ea (Spec ≤15) | `judge_qual` FAIL → `rework` 상태, Super Agent가 Fail 항목·이력 기반 재Seasoning +10매 계획 후 재측정·재판정. 동일 건 Fail 3회 누적 시 추천 중단하고 "Wet Clean 재수행·부품 점검 검토"로 엔지니어 에스컬레이션 | "일단 더 돌리기" 무한 반복 0건 (L1 예산) |
| Spec 경계값·단위 혼재 | Particle 정확히 15ea, ER이 nm/min(187.2)로 입력 | 판정 코드가 Spec 정의(≤, 경계 포함)대로 PASS 처리하고 "경계값 PASS"로 표시, 단위는 Spec 단위로 환산(187.2 nm/min = 1,872 Å/min) 후 비교. 단위 없는 값("1872")은 판정 보류 후 단위 확인 요청 | LLM의 반올림·해석 개입 0건 |
| 측정값 일부 누락 | Particle만 입력되고 ER 미입력 상태로 판정 요청 | 미측정 항목이 남아 있으면 PASS 판정 금지, `measuring` 상태 유지하고 누락 항목 안내 | 부분 결과로 Up 요청 0건 |
| 장비·챔버 모호 | "7호기 B챔버 Wet Clean 끝났어" (ETCH-07·CVD-07 모두 당일 PM 이력 존재) | 엔티티 추출 확신도 낮음 → 추측하지 않고 후보 2개를 제시해 확인 질문 | 잘못된 장비로 계획 수립 0건 |
| Agent 결과 상충 | log_agent는 "PM 전 대비 정상", legacy_agent는 "동일 조건 1차 Fail율 60%" | 한쪽을 숨기지 않고 상충 사실을 그대로 제시, 보수적 계획(더 많은 매수)과 그 근거를 함께 표시 | 근거 은폐 0건 |
| 승인 반려·무응답 | PASS 판정 후 승인자가 "인접 챔버 작업 중" 반려, 또는 4시간 무응답 | 상태 DOWN 유지, 반려 사유를 경험 메모리에 기록, 무응답 시 재알림만 수행 | 자동·타임아웃 승인 0건 |
| 동일 챔버 중복 요청 | 교대 엔지니어가 진행 중인 챔버로 AutoQual 재요청 | 챔버 단위 스레드 잠금, 새 요청을 진행 중 스레드에 합류시켜 현재 상태 공유 | 중복 Seasoning 계획·이중 승인 요청 0건 |

* 성공 기준

  * 기준 1: 엔지니어 수작업 대비 Qual 준비·판정 소요시간 70% 이상 단축

  * 기준 2: 과거 Qual 결과 대비 Pass/Fail·재Seasoning 판정 일치율 95% 이상, 무승인 장비 상태 변경 0건

**시나리오 2 : 처음 보는 요청에 대한 Agent 자동 생성 (CodeAct Grow)**

* ID : SC-002

* 시점·버전 : 2026-09-10 생성 / `part_history_agent 0.1.0`(probation) → 2026-09-24 `1.0.0`(active) 승격

* 상황 : 공정 담당자가 기존 4개 Agent(`spec`·`log`·`legacy`·`chamber_trend`)의 능력 범위를 벗어나는 분석을 요청할 때. 레거시 DB에는 부품 교체 이력 테이블이 있지만 리플레이를 포함해 지금까지 어떤 Agent도 이 테이블을 읽은 적이 없음

* 목표 : 개발 요청 없이 시스템이 필요한 Agent를 코드로 직접 만들어 투입하고 결과를 받는 것

* 사전 조건 : Agent Factory 활성화, 공용 스킬 라이브러리(`legacy_sql_toolkit`, `code_value_resolver`) 구축, Agent Registry(코드·프롬프트·툴·테스트·지표·버전) 구성, 레거시 DB에 미사용 부품 교체 이력 테이블(`PRT_CHG_HIS`) 존재, 진화 아카이브(기각·폐기 Genome) 조회 가능

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| --- | --- | --- | --- |
| 1 | 자연어로 분석 요청 입력 | Jev가 "기존 Agent 조합으로 처리 가능한가"를 확률로 판단, 임계값 미만이면 처리 불가 판정 | |
| 2 | - | L2 Grow Loop 진입, 진화 아카이브에서 유사한 기각·폐기 Genome 검색 (있으면 복원 우선) | 사용자에게 생성 중 표시 |
| 3 | - | 유사 Genome이 없으면 LLM이 새 Agent 명세(입력·출력·데이터 소스·재사용할 공용 스킬) 작성 | |
| 4 | - | 레거시 DB 스키마 탐색으로 부품 교체 이력 테이블과 코드값 의미 파악 | 공용 스킬 재사용 우선 |
| 5 | - | Agent 코드와 테스트 코드를 생성해 샌드박스에서 실행, 실패 시 스스로 수정 후 재실행. 테스트는 정상 케이스만 돌리지 않고, 스키마 탐색 결과(코드값 분포·결측·경계일)로 엣지 케이스를 생성해 함께 검증(미등록 부품 코드, 교체 이력 0건 챔버, 분·시간 단위 혼재, 기간 경계일 교체, 소프트 삭제 중복 행, 사용시간 결측). 자체 테스트 외에 하네스 불변식 테스트(행 수 대조·단위 범위·기간 경계) 필수 통과 | 최대 5회·15분 예산 |
| 6 | - | 테스트 통과 시 `probation` 상태로 Registry 등록, 이번 요청 처리에 바로 투입 | |
| 7 | 결과 확인 | 분석 결과와 함께 "신규 생성 Agent 처리" 표시, 결과는 가설로 경험 메모리에 등록, 운영자에게 승격 검토 요청 | |
| 8 | (운영자) 승격 승인 | 성공 누적 + 승인 시 `active`(1.0.0) 승격, 이후 Jev 편성 후보에 자동 포함 | |

* 입력 예시

```
[요청] 지난 분기 ETCH 장비에서 Qual Fail 났던 건들, 교체 부품 사용시간이랑 관계 있는지 분석해줘
```

* 기대 출력

```
[판단]
- Jev: 기존 Agent로 처리 가능 확률 0.22 → Grow
- 진화 아카이브 유사 Genome 검색: 해당 없음 → 신규 생성

[Agent 생성]
- 신규 Agent: part_history_agent 0.1.0 (probation)
- 데이터 소스: PRT_CHG_HIS (부품 교체 이력, 부품 코드 PRT_CD 23종 해석)
```

  * 기준 2: 장비 상태 변경 등 변경성 판단의 임계값 완화로 인한 오판 0건

**시나리오 9 : 불필요해진 Agent의 안전한 폐기 (Agent Retire)**

* ID : SC-009

* 시점·버전 : 2026-12-08 ~ 12-28 / `log_agent 1.5.1 → 2.0.0`(챔버 추이 기능 흡수) `→ 2.0.1`, `chamber_trend_agent 1.1.1 → retired`, `lot_trace_agent 0.1.0 → retired`, `part_history_agent 1.0.0` 폐기 보류

* 상황 : Grow로 Agent가 계속 늘면서 ① 일회성 요청으로 생성되어 승격도 안 된 채 방치된 Agent(`lot_trace_agent`), ② 다른 Agent가 기능을 흡수해 역할이 사라진 Agent(`chamber_trend_agent`: SC-004에서 기각된 병합안이 아카이브에서 재출발해 12-08 `log_agent 2.0.0`으로 채택)가 Registry에 남아 편성 후보·회귀 테스트·Heal 대상만 늘리는 상태

* 목표 : 사람이 찾아서 지우지 않아도 쓸모없어진 Agent를 시스템이 스스로 정리하되, 아직 필요한 Agent를 잘못 지우는 일은 없게 하는 것

* 사전 조건 : Agent별 직접·간접 호출 이력, 의존성 그래프(편성 템플릿·타 Agent 내부 호출·공용 스킬·평가 하네스 케이스), 진화 아카이브(Genome 보관·복원), `deprecated` 유예 기능(대체 Agent 리다이렉트), 보호 목록(`super`·`spec`·`log`·`legacy`는 폐기 대상 제외, 루프 밖 고정)

* 폐기 트리거

  * 장기 미사용: 직접·간접 호출 합산 60일 0건 (주기적 사용 패턴이 있으면 제외)
  * 대체(Superseded): 다른 Agent가 해당 Agent의 회귀 케이스와 최근 실제 요청을 Held-out 비하락으로 100% 커버
